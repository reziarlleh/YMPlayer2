# YMPlayer2 — правила работы

## Контекст и границы

- Название продукта в новых текстах — **YMPlayer2**, всегда слитно. Имена
  опубликованных файлов, URL, идентификаторы и исторические цитаты механически
  не переименовывать.
- Работать в рамках текущего запроса пользователя. Исходные требования:
  [стартовое ТЗ](YMPlayer_2x_Codex_Startup_Prompt.md), актуальный статус:
  [docs/PROJECT_STATUS.md](docs/PROJECT_STATUS.md), порядок:
  [docs/ROADMAP.md](docs/ROADMAP.md), нумерация: [docs/VERSIONING.md](docs/VERSIONING.md).
- Прямые уточнения пользователя имеют приоритет над исходным ТЗ и старыми
  заметками. Перечень будущих этапов в ТЗ не запускает их автоматически.
- Название приложения всегда писать слитно: **YMPlayer2**. Исторические имена
  файлов и существующие URL не переименовывать ради исправления написания.
- 2.x — самостоятельный продукт и отдельный репозиторий. Обеспечить установку
  рядом с 1.x, собственный applicationId, данные и канал обновлений.
- Репозиторий 1.x использовать как источник поведения и проверенных алгоритмов.
  Не изменять его в рамках задач 2.x и не копировать архитектуру автоматически.
- Сначала анализ, UI/UX и границы модулей; затем прототип и поэтапный перенос.
  Значимые архитектурные решения фиксировать вместе с обоснованием.

## RepoWise и память

- С начала проекта использовать глобально настроенный RepoWise. Для первого
  знакомства — overview; для дальнейшей навигации — search/context с пакетным
  запросом связанных целей. Проверять найденное в актуальных исходниках.
- После значимых изменений обновлять индекс: `repowise update` в Git-проекте;
  в обычной папке — глобальный `repowise_codex.py --ensure --refresh PATH`.
  При рассинхронизации применять `repowise doctor --repair`.
- Использовать нативную память Codex; старый agent-memory не подключать.
  Актуальные документы и фактические проверки имеют приоритет над снимками.
  Обновлять память только по прямому запросу пользователя через ad_hoc notes.

## Изменения и проверка

- README предназначен для пользователей: описание приложения, возможности,
  требования/установка, инструкции, загрузка и поддержка. Хронологию версий вести
  в [CHANGELOG.md](CHANGELOG.md), проверки/статистику тестов и внутренние планы —
  в технических документах. Не возвращать их в основное описание при обновлении.
- Рабочая память проекта: [указатель](docs/DOCUMENTATION_INDEX.md),
  [журнал работы](docs/WORK_JOURNAL.md), [ошибочные решения](docs/LESSONS_LEARNED.md),
  [багрепорт](docs/BUG_REPORT.md). В начале каждой содержательной задачи читать
  PROJECT_STATUS и ROADMAP, затем связанные записи/ADR/проверки; старые сводки
  нативной памяти не заменяют актуальный проект. Историю читать адресно.
- До завершения задачи записывать результат, проверки, неудачные подходы и их
  причины, остаток и следующий шаг в журнал и соответствующий подробный отчёт.
  При новом ошибочном решении дополнять LESSONS_LEARNED со ссылкой на доказательство.
  При прерывании сохранять конкретную точку продолжения, не только общий план.
- Не накапливать старые «текущие» статусы и будущие пункты внутри действующих
  документов. Исторические срезы маркировать/архивировать, сохранять свидетельства,
  а выполненные пункты закрывать во всех активных планах. При изменении функции
  сверять обе пользовательские инструкции, README, BUG_REPORT и карты функций/переноса.
- Перед публикацией/закрытием сверять локальный version.properties, update feeds,
  GitHub latest/описание/default branch и опубликованные документы. HTTP-проверки
  внешних зеркал датировать. Для документационной правки достаточно проверки
  ссылок/согласованности и GitHub; не запускать регрессию плеера без причины.
  Для сверки использовать `tools/Check-Documentation.py`; после push — `--github`.
  Проверка версии и ссылок не доказывает правильность описания функции: его сверять
  с исходниками, отчётом и фактической приёмкой.
- Делать небольшие связанные изменения, поддерживать документы и план в актуальном
  состоянии. После каждого законченного этапа, нового результата приёмки,
  обнаруженного неверного пути или смены приоритетов обновлять PROJECT_STATUS,
  ROADMAP, карту миграции и при необходимости README до завершения работы.
  Отделять реализованное, проверенное на эмуляторе и принятое владельцем.
  Исторические отчёты сохранять как свидетельства тогдашнего состояния,
  снабжая ссылкой на актуальный план при изменении сроков. Не создавать все
  предполагаемые модули заранее.
- Соблюдать сквозной Build из VERSIONING.md; первый APK —
  `2.0.0beta-build1` (подписанный APK создан; см. docs/M1_VERIFICATION.md).
  Для следующих версий одна запись о номере не означает наличие сборки.
- По указанию владельца от 28.10.2026 до начала цикла фиксировать `baseVersion`
  (`MAJOR.MINOR.PATCH`), цели и критерии завершения. Пока цели выбранной версии
  не закрыты, для промежуточных попыток/исправлений повышать только сквозной
  Build/versionCode: `X.Y.Z-buildN` → `X.Y.Z-buildN+1`. Следующий номер версии —
  для следующего согласованного набора целей после закрытия текущего, а не
  для каждой попытки. Каждый новый APK продукта получает новый Build; номера
  не переиспользовать. Пакет, подпись, канал и правила публикации сохраняются;
  это правило не разрешает автоматическую публикацию. Актуальные номера и
  состояние выпуска брать из VERSIONING и PROJECT_STATUS.
- По указанию владельца от 29.10.2026 описание релиза охватывает весь накопленный
  состав изменений выбранной `baseVersion`, а не только отличия последнего Build.
  Перед публикацией сверять его с целями цикла, CHANGELOG и отчётом о выполнении;
  включать все завершённые цели и исправления промежуточных Build этой версии.
  Подробные результаты отдельных попыток оставлять в технических журналах,
  а неподтверждённое и будущие функции не выдавать за готовые.
- Выполнять подходящие проверки. Результаты RepoWise не заменяют сборку,
  тесты, проверку API, APK и подписи или проверку на устройстве.
- Перенос алгоритмов делать по рабочим методам 1.x, фиксируя соответствие
  входов, выходов и обработки ошибок. Дополнительные ограничения формата ответа
  проверять на реальных данных; вымышленные фикстуры не доказывают совместимость
  протокола. Пример найденного расхождения: [M5.1](docs/M5_1_VERIFICATION.md).
- Отдельно обозначать подтверждённые результаты и ещё не проверенное поведение.

## Тема 4PDA

- Перед изменением шапки сверять действующие правила и текущую модераторскую
  структуру: [docs/FORUM_RULES_4PDA.md](docs/FORUM_RULES_4PDA.md). Сохранять
  шаблон Мастера, историю форумных вложений и явный список изменений.
- После ручных правок владельца или модератора не восстанавливать прежние
  формулировки, удалённые блоки и оформление из локальных копий. База каждой
  следующей правки — свежая серверная форма. Актуализировать точечно сведения
  нового выпуска; авторские текст, структуру и вложения сохранять. Перед
  сохранением повторно сверить серверную форму: при изменении базы заново
  наложить только необходимые правки. Не заменять шапку целиком архивным BBCode.

  спойлера, старые копии скриншотов убраны. Сохранять это оформление; не
  возвращать спойлер «Иконка» и прежние изображения из архивных копий. Для
