# YMPlayer 2.x --- стартовое техническое задание для Codex

## 0. Назначение документа

Этот документ является стартовым промптом и постоянной архитектурной
директивой для разработки **YMPlayer 2.x**.

YMPlayer 2.x --- это **новое самостоятельное приложение**, а не обычное
обновление YMPlayer 1.x. Версия 1.x остается отдельным стабильным
продуктом и продолжает получать исправления ошибок и необходимые
улучшения.

При этом YMPlayer 1.x является важным **reference/legacy source**: в нем
уже существуют проверенные работающие алгоритмы, интеграции и
пользовательские сценарии. Их необходимо изучать и, где это оправдано,
переносить в 2.x, но **не переносить старую архитектуру автоматически**.

Главная стратегия разработки:

> **Сначала спроектировать интерфейс, UX и модульную архитектуру
> YMPlayer 2.x. Затем переносить из 1.x только необходимое проверенное
> поведение и алгоритмы, адаптируя их к архитектуре 2.x. Новый
> функционал реализовывать отдельными функциональными модулями с
> минимальным влиянием на уже стабильные части приложения.**

## 0.1. Уточнения владельца проекта от 2026-09-09

YMPlayer 2.x развивается как самостоятельный продукт в отдельном
репозитории. Установка 2.x должна допускаться рядом с 1.x и не должна
заменять 1.x. Для Android это означает собственный `applicationId`,
изолированные данные и отдельный канал обновлений. Обновлятор 1.x не
должен предлагать APK 2.x. Точный идентификатор определить при создании
каркаса приложения, проверив идентификаторы 1.x.

RepoWise используется с самого начала: перед нетривиальной навигацией
по коду и межфайловыми изменениями получать overview/search/context,
затем проверять соответствующие исходники. После значимых изменений
обновлять индекс. Для Git использовать `repowise update`, для обычной
папки — глобальный launcher с `--ensure --refresh PATH`. Индекс не
заменяет сборку, тестирование и фактическую проверку поведения.

Первая планируемая версия: **`2.0.0beta-build1`**. Счётчик Build сквозной
для продукта 2.x: без сброса при смене версии или снятии beta. Формат
стабильного релиза: `2.0.0-buildN`; следующий обычный цикл разработки:
`2.0.1beta-buildM`, где `M > N`.

Рабочее правило: patch — исправления и небольшие улучшения существующих
сценариев; minor (например, `2.1.0`) — крупная новая возможность или
существенное развитие продукта. Объём релиза определять до реализации.
Подробные правила, примеры и критерии снятия beta:
[docs/VERSIONING.md](docs/VERSIONING.md).

Описанные далее этапы составляют план разработки. Их выполнение
определяется текущим запросом владельца проекта; предоставление этого
документа само по себе не означает запуск всех этапов одновременно.

-   software architect;
-   senior application developer;
-   UI/UX architect;
-   специалист по responsive/adaptive layout;

Не начинай массовое написание кода до анализа требований и

При каждом крупном изменении сначала:

1.  изучи существующую структуру YMPlayer 2.x;
2.  при необходимости изучи соответствующую реализацию YMPlayer 1.x;
3.  определи границы модуля;
4.  определи публичные интерфейсы и зависимости;
5.  оцени влияние изменения на существующие модули;
6.  предложи план;
7.  только после согласования/фиксации архитектурного решения переходи к
    реализации.

# 2. Статус YMPlayer 1.x

YMPlayer 1.x является:

-   стабильной и отдельно поддерживаемой веткой продукта;
-   источником проверенного поведения;
-   источником работающих алгоритмов;
-   источником знаний о существующих интеграциях;
-   reference implementation для сравнения результатов.

YMPlayer 1.x **не является архитектурным шаблоном для YMPlayer 2.x**.

Запрещено без отдельного обоснования:

-   копировать структуру 1.x целиком;
-   переносить крупные legacy-файлы «как есть»;
-   строить архитектуру 2.x вокруг внутренних особенностей 1.x;
-   сохранять старые зависимости только ради совместимости;
-   модифицировать репозиторий 1.x из проекта 2.x;
-   считать backward compatibility с внутренней архитектурой 1.x
    обязательным требованием.

При переносе функции из 1.x необходимо отделять:

**Что сохранить:** - пользовательское поведение; - проверенные
алгоритмы; - корректные API-взаимодействия; - обработку известных edge
cases; - накопленные исправления ошибок.

**Что не переносить автоматически:** - монолитную структуру; -
глобальное состояние; - жесткие связи между UI и бизнес-логикой; -
скрытые зависимости; - устаревшие workaround'ы; - дублирование; -
архитектурный технический долг.

# 3. Главные цели YMPlayer 2.x

## 3.1. Новый UI/UX

Первым этапом разработки должен стать **новый дизайн и новая концепция
интерфейса**.

До активного переноса функций из 1.x необходимо определить:

-   визуальный язык приложения;
-   информационную архитектуру;
-   навигационную модель;
-   основные экраны;
-   компоненты интерфейса;
-   систему размеров и отступов;
-   типографику;
-   правила адаптивности;
-   поведение интерфейса при изменении размера окна;
-   поведение при portrait/landscape;
-   поддержку разных DPI/device pixel ratio;
-   минимальные и максимальные размеры элементов;
-   правила масштабирования;
-   touch/mouse/keyboard interaction;
-   accessibility;
-   состояния loading/error/empty/offline;
-   анимации и переходы;
-   системные диалоги и уведомления.

## 3.2. Модульная архитектура

Функциональность должна быть разделена на независимые блоки.

Базовый принцип:

> **Новая функция не должна требовать изменения стабильного модуля, если
> ее можно подключить через публичный контракт, событие, сервис или
> адаптер.**

## 3.3. Контролируемая миграция из 1.x

Функции переносятся по одной или небольшими связанными группами.

Каждая миграция должна включать:

1.  анализ legacy-реализации;
2.  описание фактического поведения;
3.  выделение reusable-алгоритмов;
4.  выявление legacy-зависимостей;
5.  проектирование нового модуля;
6.  реализацию;
7.  тестирование;
8.  сравнение поведения с 1.x;
9.  документирование результата.

# 6. Responsive / Adaptive UI --- обязательные правила

Интерфейс не должен проектироваться под одно фиксированное разрешение.

Нельзя считать конкретную ширину/высоту экрана основной архитектурной
единицей.

Используй:

-   layout constraints;
-   anchors/alignment;
-   flex/grid-подобные механизмы доступного framework;
-   relative sizing там, где это оправдано;
-   min/max constraints;
-   breakpoints только там, где действительно меняется композиция;
-   reusable layout components;
-   design tokens.

## 6.1. Классы размеров

Определи логические классы viewport, например:

-   compact;
-   medium;
-   expanded;
-   large.

Конкретные границы должны быть выбраны после анализа используемого UI
framework и целевых платформ.

Не привязывай бизнес-логику к breakpoint'ам.

## 6.2. Ориентация

Для каждого ключевого экрана опиши поведение:

### Portrait

-   приоритет вертикального потока;
-   нижняя/компактная навигация, если уместно;
-   второстепенные панели могут сворачиваться;
-   player controls должны оставаться доступными.

### Landscape

-   эффективно использовать дополнительную ширину;
-   допускается двух-/трехпанельная композиция;
-   не растягивать контент бессмысленно на всю ширину;
-   применять max-content-width там, где это улучшает читаемость.

## 6.3. Масштабирование

Не масштабируй весь UI как bitmap.

При изменении пространства должны адаптироваться:

-   количество колонок;
-   расположение панелей;
-   плотность информации;
-   размеры artwork;
-   длина видимого текста;
-   расположение controls.

При этом интерактивные элементы должны сохранять удобный hit target.

## 6.4. Текст

Предусмотреть:

-   длинные названия треков;
-   длинные имена артистов;
-   локализацию;
-   увеличение системного размера шрифта;
-   ellipsis/wrapping по контексту;
-   отсутствие наложения текста на controls.

## 6.5. Safe areas

Учитывать:

-   status/navigation bars;
-   display cutouts;
-   rounded corners;
-   системные панели;
-   виртуальную клавиатуру;
-   desktop window decorations, если применимо.

# 9. Правила модульности

Каждый функциональный модуль должен иметь:

1.  одну четко определенную область ответственности;
2.  минимальный публичный API;
3.  скрытые внутренние детали реализации;
4.  явные зависимости;
5.  возможность тестирования независимо от UI;
6.  отсутствие прямого доступа к internals другого модуля.

Предпочтительное направление зависимостей:

``` text
UI
 ↓
Application / Use Cases
 ↓
Domain / Contracts
 ↑
Adapters / Infrastructure
```

Domain/Core не должен зависеть от конкретного UI framework, сетевой
библиотеки или storage implementation без веской причины.

------------------------------------------------------------------------

# 10. Контракты между модулями

Используй:

-   interfaces/protocols;
-   dependency injection;
-   events;
-   immutable DTO/model objects там, где это разумно;
-   service abstractions.

Избегай:

-   глобальных mutable singleton;
-   прямого импорта внутренних классов другого модуля;
-   скрытых side effects;
-   циклических зависимостей.

Пример:

``` text
Player Module
     │
     ├── playback_state_changed
     ├── track_changed
     ├── position_changed
     └── queue_changed
              │
              ▼
       заинтересованные модули
```

Lyrics, scrobbling, history, Discord integration и другие будущие
функции должны по возможности подписываться на публичные события, а не
встраиваться непосредственно во внутренний код Player.

------------------------------------------------------------------------

# 11. Provider abstraction

Не связывай Core приложения жестко с конкретной реализацией Yandex Music
API.

Предусмотри абстракцию типа:

``` text
MusicProvider
    ↑
YandexMusicProvider
```

Контракт может предоставлять операции вроде:

-   authentication;
-   search;
-   get_track;
-   get_album;
-   get_artist;
-   get_playlist;
-   get_stream_info;
-   get_recommendations;
-   get_user_library.

Фактический набор методов определить после анализа 1.x и требований 2.x.

Это не означает обязательную поддержку других сервисов прямо сейчас.
Цель --- не смешивать provider-specific код с core/domain.

------------------------------------------------------------------------

# 12. Player Core

Player должен рассматриваться как отдельная подсистема.

Разделить, насколько позволяет стек:

-   queue management;
-   playback state;
-   audio backend;
-   stream resolving;
-   buffering;
-   position/duration;
-   repeat/shuffle;
-   media session;
-   history;
-   UI representation.

UI не должен непосредственно управлять низкоуровневым audio backend.

Предпочтительно:

``` text
UI
 ↓ commands
Player Service
 ↓
Audio Backend Adapter

Audio Backend
 ↓ events
Player Service
 ↓ state/events
UI
```

------------------------------------------------------------------------

# 13. Состояние приложения

Определи единую стратегию state management.

Не допускай ситуации, когда одна и та же сущность имеет несколько
несогласованных источников истины.

Для каждого state определить owner.

Например:

-   playback state → Player;
-   authentication state → Authentication;
-   user library state → Library;
-   UI-only temporary state → соответствующий UI component/view model.

State должен обновляться предсказуемо и наблюдаемо.

# 14. Перенос функции из YMPlayer 1.x

Для **каждой** переносимой функции выполняй следующий workflow.

## Шаг A --- исследование

Найди реализацию в 1.x и опиши:

-   входы;
-   выходы;
-   зависимости;
-   side effects;
-   обработку ошибок;
-   edge cases;
-   связанные настройки;
-   сетевые вызовы;
-   кеширование;
-   UI coupling.

## Шаг B --- поведенческая спецификация

Зафиксируй, **что делает функция**, независимо от того, как она
реализована.

## Шаг C --- reusable logic

Определи, какие алгоритмы можно перенести почти без изменений.

## Шаг D --- legacy debt

Определи, что переносить нельзя или нецелесообразно.

## Шаг E --- место в 2.x

Определи:

-   модуль;
-   публичный контракт;
-   необходимые события;
-   зависимости;
-   модели данных.

## Шаг F --- реализация

Перенеси алгоритм, адаптировав его к архитектуре 2.x.

## Шаг G --- проверка

Сравни поведение 1.x и 2.x на одинаковых сценариях.

## Шаг H --- документация

Обнови `docs/MIGRATION_MAP.md`.

# 16. Новый функционал

Новый функционал не должен внедряться хаотично в существующие файлы.

Перед реализацией новой функции ответь:

1.  Это новая responsibility или расширение существующей?
2.  Можно ли реализовать ее отдельным модулем?
3.  Какие публичные данные ей нужны?
4.  Какие события ей нужны?
5.  Требует ли она изменения существующего публичного контракта?
6.  Можно ли избежать изменения стабильного модуля?
7.  Как функция будет отключена/удалена без разрушения приложения?

Если новая функция требует большого количества изменений в несвязанных
модулях --- это сигнал проверить архитектуру.

------------------------------------------------------------------------

# 17. Стабильность модулей

После того как модуль реализован, протестирован и признан стабильным:

-   минимизировать изменения его internals;
-   новые функции подключать через contracts/events;
-   изменение public API делать осознанно;
-   при изменении контракта анализировать всех consumers;
-   не проводить unrelated refactoring одновременно с добавлением
    функции.

Принцип:

> **Working stable code is a protected asset, but not an excuse for bad
> architecture.**

Если изменение действительно необходимо --- сначала объясни причину и
влияние.

------------------------------------------------------------------------

# 18. Тестирование

Архитектура должна позволять тестировать бизнес-логику без полноценного
запуска UI.

Предусмотреть:

-   unit tests;
-   module tests;
-   integration tests;
-   UI/component tests там, где поддерживается;
-   regression tests для перенесенных алгоритмов.

Для критичных функций, переносимых из 1.x, по возможности создать
тестовые сценарии до или одновременно с переносом.

Особое внимание:

-   queue;
-   shuffle/repeat;
-   восстановление состояния;
-   network failures;
-   expired authentication;
-   unavailable tracks;
-   malformed API responses;
-   cache invalidation;
-   interrupted playback;
-   orientation/window resize;
-   lifecycle/background/foreground.

------------------------------------------------------------------------

# 19. UI regression matrix

Для ключевых экранов определить набор проверок минимум по категориям:

  Параметр     Проверки
  ------------ -----------------------------------------
  Размер       compact / medium / expanded
  Ориентация   portrait / landscape
  DPI          normal / high
  Text scale   default / enlarged
  Theme        light / dark, если поддерживается
  Content      short / long text
  State        loading / loaded / empty / error
  Input        touch / mouse / keyboard, где применимо

Не требуется создавать десятки почти одинаковых layout'ов. Цель ---
проверить устойчивость системы адаптивных правил.

# 20. Производительность

При проектировании учитывать:

-   lazy loading;
-   virtualized lists;
-   image caching;
-   cancellation устаревших network requests;
-   debounce/throttle для поиска;
-   отсутствие тяжелой работы на UI thread;
-   controlled background work;
-   минимизацию ненужных rebuild/re-render;
-   корректное освобождение ресурсов audio/image/network.

Не заниматься premature optimization, но не создавать заведомо не
масштабируемые решения.

Не логировать секреты, токены и чувствительные данные.

Ошибки должны содержать достаточно контекста для диагностики.

# 24. Правила работы с кодом

1.  Не делай огромных рефакторингов без необходимости.
2.  Делай изменения небольшими логическими этапами.
3.  Не смешивай несколько независимых задач в одном изменении.
4.  Не удаляй рабочее поведение без явной причины.
5.  Не создавай compatibility layer с 1.x без необходимости.
6.  Не добавляй abstraction только «на будущее», если у нее нет понятной
    роли.
7.  При этом границы ключевых подсистем должны быть определены заранее.
8.  Избегай magic numbers.
9.  Избегай дублирования.
10. Соблюдай naming convention проекта.
11. Публичные контракты документируй.
12. После изменения запускай релевантные проверки/tests.
13. Не маскируй failing tests изменением теста, если ошибка находится в
    реализации.

# 25. Git strategy

YMPlayer 2.x имеет отдельный репозиторий.

YMPlayer 1.x продолжает жить независимо.

Желательно зафиксировать commit/tag 1.x, относительно которого началось
проектирование 2.x.

Если позже исправление из 1.x актуально для 2.x:

-   сначала изучить commit;
-   определить, существует ли аналогичная ошибка в 2.x;
-   переносить **смысл исправления**, а не автоматически cherry-pick'ать
    код, если архитектуры уже разошлись.

# 26. Definition of Done для модуля

Модуль считается завершенным, когда:

-   responsibility четко определена;
-   public API минимален и понятен;
-   отсутствуют ненужные зависимости;
-   реализованы необходимые состояния ошибок;
-   UI не зависит от internals;
-   tests проходят;
-   документация обновлена;
-   migration map обновлена, если это перенос;
-   нет известных regression относительно требуемого поведения;
-   responsive UI проверен, если модуль имеет UI;
-   код не содержит временных hacks без зарегистрированного технического
    долга.

# 30. Финальная директива

Цель проекта --- не просто «переписать YMPlayer 1.x красивее».

Цель --- создать **долгоживущую модульную платформу YMPlayer 2.x**, в
которой:

-   интерфейс современный и адаптивный;
-   UI корректно работает на разных разрешениях и ориентациях;
-   функциональные подсистемы изолированы;
-   проверенные алгоритмы 1.x используются повторно там, где это
    рационально;
-   технический долг 1.x не переносится автоматически;
-   новый функционал можно добавлять отдельными блоками;
-   стабильные модули требуют минимального вмешательства;
-   архитектура остается понятной через месяцы и годы развития.

**Начни с анализа и проектирования UI/UX. Не начинай массовый перенос
legacy-кода до утверждения новой концепции интерфейса и базовой
архитектуры.**
