# Пауза и сохранение подготовленной очереди волны — 2.6.6

11 ноября2026. Продолжение B-047 после отрицательного отзыва владельца о129.
После Bluetooth-паузы ожидалась середина выбранного трека, а через несколько
часов при открытии оказалось0:00. Не установлено, был ли это тот же трек.
Проверка немедленного force-stop и проверка одного флага playing не закрывают
этот случай. Stable/Latest/feeds остаются2.6.5-build125.

## Воспроизведённые причины

1. `recoverWaveTrack` назначал переход через300ms после ошибки. Pause запрещала
   Play, но не сам переход: следующий трек выбирался с0s и попадал в checkpoint.
   Native-проба на исходнике129: ошибка при7s→controller Pause→после задержки
   ID1 сменился наID2. [Отрицательная проба](qa/wave-paused266/red-error-pause-api28.txt).
2. Подготовка метаданных после перемотки считалась поводом продолжать волну:
   `userCommanded` означал любую команду, включая seek, а не действующий Play.
   При ошибке тихой подготовки и наличии готового следующего файла снова
   выбиралсяID2 вместоID1. [Отдельный отказ](qa/wave-paused266/red-metadata-api28.txt).
3. Метаданные десяти записей уже сохранялись, но `WaveAudioBuffer.clear()` при
   detach/restore удалял полные файлы. Новый процесс также удалял старую папку
   cacheDir/wave-audio. Поэтому сохранённая очередь не была сохранённой
   предзагрузкой: повторное открытие зависело от получения аудио по сети.

Это подтверждённые механизмы приложения, а не диагноз модели телефона/ГУ
или доказательство точного порядка событий на физическом устройстве владельца.

## Изменения

Pause, noisy и потеря аудиофокуса отменяют отложенный автоматический переход,
сохраняя выбранный трек и позицию. Позднее заполнение очереди добавляет будущие
записи, не выбирает другую текущую. Явно запрошенный пользователем Next остаётся
отдельным действием: последующая Pause запрещает звук, но не отменяет его выбор.
Play после паузы на конце трека продолжает подготовленным следующим, не начинает
завершённый трек сначала. Ошибка автоматически пропускается только при действующем
запросе воспроизведения; seek/metadata-only restore не создают этот запрос.

Полные файлы окна сохраняются в частной папке приложения filesDir/wave-audio.
Индекс хранит профиль, аккаунт, ID, имя файла и длину; токенов и сетевых URL нет.
После проверки MediaExtractor файл синхронизируется на накопитель и переименовывается,
затем индекс публикуется через AtomicFile. Незавершённые .part не читаются.
При новом адаптере индекс читает только существующие файлы ожидаемой длины.
Файлы другого аккаунта недоступны. Имена из индекса ограничены именами файлов
в этой папке; произвольные пути не принимаются.

Detach/restore отменяют незавершённые загрузки, сохраняя полные файлы. Вместе
с существующим checkpoint восстанавливаются все записи окна, текущий ID,
позиция, режим Play/Pause/Stop, станция, настройки, batch/session/cursor и фильтр
ранее выбранных треков. Полное окно не запрашивается заново: при отсутствии сети
оно может продолжить сохранённый Play из файлов. Сохранённая Pause остаётся тихой.

Окно по-прежнему ограничено10 записями вместе с предыдущим треком. Старые файлы
уходят по мере продвижения; новые рекомендации запрашиваются для освободившихся
мест. Если готовый будущий файл утрачен/укорочен, ремонтируется эта запись
сохранённой очереди, без подмены её новой рекомендацией. Пока Pause, выбор и
позиция не меняются. По уточнению владельца явный Stop полностью очищает окно, файлы и session/cursor;
следующий Play начинает новую подборку. Долговечный Stop также отбрасывает старый
checkpoint очереди при миграции или прерванной записи. Уже услышанная история
сохраняется, старые непрослушанные будущие треки не считаются прослушанными.
Применение настроек через «Слушать волну» сразу прерывает старый трек и запускает
новую волну с выбранными параметрами. Старое окно и запоздалые ответы удаляются.
Смена выбора без применения по-прежнему только сохраняет настройки. После Stop
и сенсорный Play, и MediaSession Play используют актуальные выбранные настройки.
Выбор другого источника очищает прежнее окно.
Постоянный офлайн-кэш лайков, USB/обычные плейлисты, радио и клипы не перерабатываются.

## Исправления тестовых сценариев

Первый вариант fault injection подменял URI текущего MediaItem. Такое изменение
само могло обнулить позицию при последующей синхронизации Media3. Проверка заменена
отказом реального resolver при неизменном MediaItem: удалён готовый файл и недоступен
поток текущего трека. При7s по-прежнему проверяется строго тот же ID и7s, JSON
checkpoint и новое создание движка. Для noisy вызывается настоящий callback
Media3; отдельный cold/service-тест использует настоящий защищённый системный broadcast.

Старый EOF-тест допускал тихий выбор следующего после Pause: теперь сохраняется
прежний ID. Только на границе EOS разрешено округление на1s к последнему аудиосэмплу;
проверки середины трека остаются точными. Сетевой retry проверяется по типизированной
диагностике и продолжению, а не по одновременному отображению кратковременной ошибки
и конкретного ID. Старое ожидание удаления всех файлов при restart заменено
требованием сохранения всех10 без новых загрузок.

## Границы результата

Эмуляторные fixtures не доказывают полудневный простой физического смартфона
владельца. Безусловного Play, имитации Pause→Play и новой настройки автозапуска нет.
Сохранение файлов помогает при подключающемся интернете, пока хватает готового окна;
новые рекомендации и отсутствующее аудио требуют доступа к сервису. Уже утраченную
старым APK позицию восстановить из пустого checkpoint невозможно.
