## Подтверждённые причины и изменения

| Наблюдение | Причина в коде | Изменение |
|---|---|---|
| D-006: feedback/контекст волны | Современная session-выдача сопровождалась station/form feedback; sessionId не сохранялся в WaveTrack; timestamp был строкой Unix seconds, dislike без длительности | JSON и endpoint выдававшей трек сессии; ISO8601 UTC; числовая длительность; индивидуальный sessionId в очереди и checkpoint |
| D-007: пустой кэш без аккаунта оставлял LIST | restoreOfflineQueue выходил до фиксации явно выбранного OFFLINE | Headless-выбор фиксирует пустой OFFLINE без запуска старого списка |
| D-009: Play терялся при пересоздании службы | detach безусловно supersede/cancel незавершённого foreground-запроса | Только действительный ожидающий Play переносится на новый attach; более поздние Pause/Stop/смена профиля сохраняют приоритет |
| B-052: существующий движок оставался disconnected | connected выставлялся только при загрузке очереди; пустой сохранённый OFFLINE мог не загрузиться | attach отражает реальное подключение независимо от доступных метаданных |
| B-053: локальный список не включался из офлайна | Доступность нового списка проверялась с origin старого OFFLINE | Проверка по запрошенному источнику до атомарного выбора; offline owner снимается после успешного перехода |
| B-054: холодный Вкл не запускал сохранённую Pause в149 | После раннего connected метаданные ещё отсутствовали; playOnInterfaceOpen принимал их за пустой список | Явный запрос Вкл ожидает метаданных с profile/revision fence, переживает замену движка и отменяется новой Pause |

В core добавлено необязательное поле WaveTrack.sessionId с совместимым значением
по умолчанию. provider/yandex владеет сериализацией протокола; playback/android —
сохранением очереди и жизненным циклом. Прямых UI-зависимостей между этими модулями
не добавлено. Для старых checkpoint без waveSessions используется прежний общий
waveSession; явно пустой sessionId отдельного legacy-трека остаётся пустым.
Формат переносимого пользовательского кэша не меняется.

## Протокол волны и границы вывода

Сопоставлены первичные исходники действующих клиентов:
[rotor_sessions.py](https://github.com/MarshalX/yandex-music-api/blob/main/yandex_music/_client/rotor_sessions.py),
[SessionEvent](https://github.com/MarshalX/yandex-music-api/blob/main/yandex_music/rotor/session_event.py),
[документация session feedback](https://ym.marshal.dev/yandex_music._client.rotor_sessions/),
[история изменения station feedback](https://github.com/jrfrigat/YandexMusic/blob/main/CHANGELOG.md).
Локальные снимки прочитаны 18 ноября; SHA256 rotor_sessions:
`a9f589f10bca12e7c37e340e740c65fe2dc59a6a5634c0f6dfc0caed63804008`,
SessionEvent:
`501dabf3712eb5dab6d485e6faf9a43fed0dda2813a78154a63a258d95d30eb4`.
Это первичные исходники клиентов неофициального API, не гарантия Яндекса.

Проверяются оба endpoint, пять типов событий, ISO8601 UTC, JSON content type,
числовая длительность и контекст двух разных сессий после холодного восстановления,
а также миграция checkpoint с одним общим sessionId. Запросы личным токеном не
выполнялись. Нельзя приписать каждому старому HTTP400/NO_PROGRESS именно эту
причину, обещать отсутствие повторных рекомендаций или исправление DNS/TLS сервера.

Жизненный цикл сверялся также с
[Media3 background playback](https://developer.android.com/media/media3/session/background-playback).
Destroy/release сервиса сам по себе не является новой командой Stop пользователя.
Сохранённый Play без настоящего foreground-запроса по-прежнему не запускает звук.

## Чистка и оптимизация

- Удалён только internal CatalogMetadataIndex.clearLocation: нет вызовов в main,
  test/androidTest, Java/XML или строковых/reflection ссылок. clear(owner,location)
  и фактическая очистка индекса сохранены; пользовательские файлы не удалялись.
- RepoWise safe-only выдал12 кандидатов, но ни одного готового к безопасному
  удалению. Дополнительный поиск приватных имён не дал кандидатов; экспортных —
  только названный метод. Android callbacks, entry points и LruCache.sizeOf
  сохранены. Это не заявление, что во всём проекте отсутствует неиспользуемый код.
- Заглушек активного функционала не найдено: найденные placeholder относятся
  к резервному изображению и SQL-параметрам. Старое удаление файла radio probe
  является очисткой прежнего формата, не работающей проверочной утилитой.
- Возможная будущая оптимизация: WaveLoader принимает один пригодный элемент
  серверного пакета за шаг; окно из10 может потребовать нескольких запросов.
  Можно исследовать ограниченный буфер остатка пакета с session/cursor/profile
  fences. В этом цикле алгоритм выдачи не переписан, ускорение не измерялось.
- Возможная уборка приватных поколений metadata-index требует отдельной оценки
  их lease/ownership. Без подтверждённой проблемы не затрагивалась.
- Не выполнялись обновления зависимостей, объединение модулей, удаление ABI,
  ослабление checksum или изменение формата переносимого аудиокэша ради чистки.

## Дополнительная проверка и остаток

Подписанный149 не прошёл холодный ON/saved Pause на23/35: время осталось15s,
транспорт PAUSED, в журнале STARTUP_ON без Play. Это регрессия B-052, а не сбой
пользователя. [Red23](qa/triage-20261117/signed149-api23-red.json),
[red35](qa/triage-20261117/signed149-api35-red.json).149 не публиковался;
исправление B-054 проходит в новом Build150 той же2.8.3.

Дополнительные старые фикстуры LocalPlayback нормализованы: встроенный Local
вместо owner, последовательное ожидание смены профилей, явная sessionPause при
проверке порядка команд во время IO (кнопка, показывающая Play, обязана посылать
Play), legacy AudioManager на23, сравнение экземпляров движка вместо пропускаемого
короткого disconnected. Проверки позиции/очереди/отсутствия полного сканирования
не ослаблялись. TvExtender-тесты ограничены26+, как его
[реализация AndroidX](https://android.googlesource.com/platform/frameworks/support/+/refs/heads/androidx-main/core/core/src/main/java/androidx/core/app/NotificationCompat.java).

Оставлено новое наблюдение **D-011**: plain framework MediaBrowser на API23
подключается к корню, но не получает каталог. Повторено на свежих данных,
современный Media3 browser работает. Callback AudioService идентичен148;
временный trace onGetChildren не был вызван и удалён.
[QA/границы](qa/triage-20261117/legacy-browser23.json),
[отрицательная проба](qa/triage-20261117/api23-fresh-browser-baseline.json).
В [первичном коде моста](https://github.com/androidx/media/blob/release/libraries/session/src/main/java/androidx/media3/session/legacy/MediaBrowserServiceCompat.java)
до28 используется общий framework controller, а
[LibraryStub](https://github.com/androidx/media/blob/release/libraries/session/src/main/java/androidx/media3/session/MediaLibraryServiceLegacyStub.java)
может вернуть null до callback, если не найден controller. Это гипотеза причины,
не доказанный runtime stack. Для24–27 и физических устройств вывод не делается.
Этот путь не назван исправленным; изменение мостов/доступа контроллеров или
замена Media3 оставлены отдельной задачей. Две неподдержанные TV-пробы на23
не смешиваются с этим сохраняющимся отказом.
