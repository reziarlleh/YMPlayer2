## Поведение

- Вместо фиксированных Основной/В дороге/Гость — список людей с созданием,
  переименованием и удалением с подтверждением. Последнего удалить нельзя.
  Выбор через прежнюю кнопку профилей; все пользователи могут войти в Яндекс
  либо пользоваться локальными файлами без аккаунта.
- Переименование сохраняет ID, сессию и данные. Введённое имя не переводится,
  даже если оно совпало с прежним названием «Основной».
- При переключении открывается плеер на паузе с очередью/позицией выбранного
  пользователя. Старое ожидающее восстановление/поздний ответ не запускает
  прежний профиль. Авторизация и пользовательские коллекции разделены по ID.
- У каждого свои язык, тема, выбранный скин и масштаб. Установленные пакеты
  скинов, подключённые папки, разрешения, качество звука и физическая папка кэша
  остаются общими для устройства. Одинаковый аккаунт Яндекса естественно имеет
  общую серверную коллекцию; профили не создают отдельные Яндекс-аккаунты.
- Удаление активного пользователя переключает на первого оставшегося на паузе,
  удаляет его сохранённый вход, локальные коллекции, историю и личные настройки.
  Музыкальные файлы/общие папки, в том числе физические аудиокопии, не удаляются.

## Хранение и миграция

core/UserProfiles сериализует CRUD через Mutex и публикует список после записи.
NonCancellable завершает уже начатую мутацию при закрытии экрана; общий busy
блокирует повторный выбор пользователя во время удаления даже после смены
корневой композиции. Имя не используется в путях/ключах, новые ID — UUID.
library/local/LocalUserProfiles хранит AtomicFile user-profiles.json/schema1.
Повреждённый список не перезаписывается defaults; изменение временно блокируется.

Прежние ID owner/road/guest сохраняются вместе с ключами аккаунтов, очередей,
плейлистов и кэша. Отображаемые имена становятся Пользователь1/2/3, специальный
guest-запрет входа снимается. На чистой установке один пользователь.
Общие значения оформления2.7 используются как начальные значения миграции;
новые изменения пишутся в персональные ключи. AppLanguages/масштаб/скин наблюдают
смену ID; ShellApp получает новую корневую композицию и сохранённую тему.

AccountAuth в продукте получает динамический список, сохраняет совместимый
конструктор для фиксированных тестовых каталогов и отвергает поздние результаты
удалённого аккаунта. Удаление неактивного пользователя не инвалидирует запросы
текущего. AndroidPlayback при отсутствующем выбранном ID выбирает первого
существующего, а не восстанавливает удалённый owner.
Новых модулей, разрешений Android и алгоритмов сети/волны не добавлено.

## Найденные ошибки реализации и тестовых условий

- Первая сборка: новый callback в конце AccountAuth менял привязку старых
  trailing lambda now; сохранён прежний конструктор и добавлен отдельный overload.
- UI сначала сохранял пользователя, но продолжение после IO приходило к
  ExoPlayer вне его application thread. Отрицательные UI-прогоны23/35 и
  [типизированный след](qa/profiles280/profile-thread-red.txt) это показали.
  CRUD-корутина явно использует Main.immediate; повтор полного UI-цикла прошёл.
- Первоначальный forgetProfile инвалидировал запросы и нового активного
  пользователя. [Отрицательный JVM](qa/profiles280/inactive-delete-red.txt)
  подтверждает ошибку; поколение меняется только при удалении активного аккаунта.
- Синтетический DPAD-тест забывал выйти из touch mode. Добавлены настоящее
  KEYCODE_DPAD_DOWN, проверка фокуса и активация Center; код кнопки не менялся.
- Старый launch-тест ожидал сетевой отказ при готовом аудио волны: оно корректно
  продолжало играть. После явного удаления только fixture-аудио появились
  AUDIO_PREPARE/error, а не обязательный waveIssue. Условие теперь требует
  реального NETWORK/LAUNCH_RESUME_WAIT и остановившегося движка. Отмену при
  смене профиля проверили повторно, с успешным результатом на23/35.
- Тот же старый helper имел AudioFocusRequest в синтетической сигнатуре,
  мешая загрузке класса на23. Фикстура использует Any и настоящий legacy API
  до26; focus-cancellation прошёл на23/35. Это изменения тестов, не новый
  обход пользовательской Pause и не исправление отложенного случая Fox_7.

Начальные отрицательные логи сохранены в qa/profiles280; успешно пройденные
методы в частично отрицательном наборе дополнены адресным повтором оставшегося
метода. Точные файлы перечислены в verification.json. Ошибку UID-парсера
проверки upgrade35 (appId вместо userId) исправили до положительного повторения.
RepoWise context/update не загрузились из-за tree_sitter; проверены сами
исходники, сборки и устройства эмуляции. Индекс не объявляется свежим.

Первый UI-прогон подписанного139 на35 перекрыло системное ANR-окно
«System UI isn't responding» из пакета android, поэтому SDK не нашёл кнопку
профилей. [Снимок UI-иерархии](qa/profiles280/api35-139-systemui.xml) и
[отрицательный прогон](qa/profiles280/api35-139-systemui-red.txt) сохранены.
После выбора Wait полный UI-сценарий на том же APK прошёл; код и условия
успешного результата не менялись. Это не засчитано как crash приложения.
