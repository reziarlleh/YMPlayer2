# Холодный переход в офлайн — 2.6.4-build124

30 октября2026. Доработка B-041 завершена в той же2.6.4 и опубликована.
Предыдущий123 сохранён в релизах;122 остаётся отозванным. Форум отложен:
новых сообщений, правок шапки и вложений не было. Этот отчёт заменяет текущий
статус холодного пути; [результаты123](CLIPS_OFFLINE_2_6_4_VERIFICATION.md) сохраняются как история.

## Почему возникала задержка

- В123 restoreOfflineQueue ждал readyTracks до смены origin. В119 origin
  переключался раньше. Это подтверждённая регрессия видимого ответа на нажатие.
- Холодный SAF-каталог делал6–9 отдельных stat-запросов и открывал JSON каждого
  трека. При отсутствии обложки lookup копировал и искал весь список детей:
  квадратичная работа. Catalog.ready публиковался после всего обхода.
- Общий store mutex удерживался на чтении каталога, задерживая выбранный файл.
- Offline-команда могла ждать постороннее сканирование локальной/USB-медиатеки.
- Прежние latency-тесты заранее ждали ready и подготавливали audio proof.
  Они доказывали готовый Play/Next, но не первый вход. Поэтому закрытие всего
  B-041 в123 было неверным; вывод исправлен и покрыт отдельными проверками.

Вклад каждого ожидания на устройстве владельца не измерен. Не утверждается,
что все storage-расходы появились именно в123: сравнением119/123 доказан перенос
UI-переключения, прочие затраты найдены в текущих исходниках.

## Реализация

StorageNode получает id/name/MIME/size/mtime одним bulk inventory; отсутствующие
дети ищутся через map. LikedFileStore читает каталог вне mutex выбранного аудио.
App-private индекс разделён по owner/location/schema и сохраняется AtomicFile.
При новом холодном открытии всегда читается свежий inventory. Неизменённые JSON
не открываются повторно; неизвестные/изменённые строки читаются с накопителя.
Перед собственной записью строка инвалидируется долговечным журналом, в том
числе при одинаковых size/mtime. Журнал затем уплотняется без O(N²) перезаписи.

При повреждённом/отсутствующем индексе или неизвестном/нулевом mtime применяется
безопасное чтение метаданных. Индекс не даёт прав доступа и не заменяет SHA
выбранного аудио. URI/size/mtime для audio integrity читаются заново. Первая
миграция старого каталога всё ещё читает JSON один раз. Внешнюю подмену JSON,
сохранившую точные URI/size/mtime, один индекс атрибутов отличить не может.

Core хранит отменяемый loadJob. UI сразу выделяет Offline и показывает подготовку,
не ожидая чужой local/USB scan. Origin, очередь и закладка меняются только после
готовности каталога нужного владельца. Stop, новая команда, смена профиля/аккаунта,
отключение кэша и отсоединение движка отменяют ожидание без позднего автозапуска.
Реальный EOF исходящей волны не отменяет уже запрошенный Offline.
Использованы существующие переводы подготовки во всех8 языках; новых строк нет.

## Найденная при проверке гонка

Снятие общего catalog mutex разрешило новому лайку скачаться до публикации
старого inventory. Файл оставался, но готовый трек исчезал из state.tracks.
Storage generation защищал запись индекса, а не возврат списка клиенту.
Автоскачивание теперь ждёт начального ready. Cancel не возобновляет отменённые
скачивания после восстановления каталога; новый лайк разрешает новую попытку.
Ошибка чтения сохраняет pending для ручного повтора; ручной sync уже ждёт ready.
Пять новых JVM cases фиксируют snapshot до gate: новый лайк, Cancel, новый Like
после Cancel, clear и ошибка чтения→ручной sync. На de93ddf два сценария теряли
трек; после правки23/23 OfflineMusicTest и156 core прошли.
[Red](qa/cold-offline264/like-race-before.json), [green](qa/cold-offline264/like-race-after.json).

не заявляется. Новый/изменённый файл проверяется полностью, медленный накопитель
не обещан мгновенным. Исправления остальных шести целей2.6.4 сохранены в полном

его собственное вспомогательное дерево, commit и push затем завершились.
