# Независимые переносимые офлайн-кэши — требования и проект миграции

14 ноября 2026. Владелец определил цель после разбора текущего кэша 2.8.0-build144.
Первоначальная спецификация реализована в ручном кандидате 2.8.1:
[план](PLAN_2_8_1.md), [исходники, проверки и ограничения](OFFLINE_CACHE_2_8_1_VERIFICATION.md).
Stable/Latest/feed пока сохраняют 2.8.0-build144. Ниже — согласованные требования.

## Уточнения владельца

- Каждый Яндекс-профиль имеет собственный независимый кэш и собственный выбор
  расположения: стандартная внутренняя папка либо выбранная пользовательская.
  Можно одновременно использовать стандартные и пользовательские расположения
  в разных профилях. Перенос и очистка одного не затрагивают остальные.
- **Включение офлайн-кэша, Wi-Fi и качество скачивания остаются общими для устройства.**
  Первоначальный ответ о разделении всех настроек отменён владельцем в той же беседе.
- **Индивидуальная настройка папки доступна только при глобально включённом кэше.**
  При выключении нельзя запускать подключение, преобразование, перенос,
  синхронизацию или использовать постоянный кэш для новых запросов воспроизведения.
  Прежние пути и файлы сохраняются до включения или отдельной явной очистки.
  Ограничение должно действовать и в контроллерах/службах, не только в UI.
- Стандартные каталоги находятся в приватном filesDir и удаляются Android вместе
  с приложением. Пользовательские — в общей папке устройства или на USB вне
  app-specific storage; их файлы сохраняются после удаления приложения.
  Выбор ограничен доступными Android папками и возможностями SAF-провайдера.
- Выбранный существующий кэш нужно распознавать, подключать и при необходимости
  преобразовывать. Поддержать папки после переустановки и копирования с другого
  устройства. Уже исправное аудио повторно не скачивается.
- Встроенный Локальный остаётся плеером файлов/USB без Яндекс-аккаунта. Привязка
  аккаунтного кэша относится к соответствующему Яндекс-профилю.

## Принятый переносимый формат

Менять аудиоформат не требуется. Существующие .audio, .cover, JSON и контрольные
суммы можно сохранить; меняются описание каталога и способ привязки.

В каждом самостоятельном корне хранится ymplayer2-cache.json: applicationId,
format=2, постоянный cacheId и accountUid Яндекса. Структура трековых JSON
сохранена; дополнительный отдельный номер метаданных не вводился.
Имя аккаунта не используется как ключ. Локальный UUID профиля и абсолютные
пути/URI не должны определять принадлежность переносимых файлов. Токены и другие
данные входа в кэш не включать. Файлы внутри корня адресуются относительно него.
Локальный ускоряющий индекс перестраиваемый, переносить его для работы не нужно.

Приватная настройка приложения сопоставляет profileId/аккаунт с выбранным корнем.
На другом устройстве создаётся новая локальная привязка к тому же cacheId/UID.
Один физический корень нельзя одновременно назначать разным профилям этого
приложения. В общей родительской папке можно создавать разные самостоятельные
подпапки. Копии кэша на разных устройствах работают независимо.

## Обычное обновление поверх 2.8.0

Прочитать прежний общий путь, сохранённые профили и доступные UID аккаунтов.
Для каждой известной пары вычисляется прежний каталог SHA256(profileId + NUL +
accountId). Его можно описать новым паспортом и привязать к профилю на месте,
без перемещения всех аудиофайлов и без скачивания. Существующее внешнее размещение
сохраняется; стандартное остаётся внутренним. Общие переключатели не меняются.

При выключенном глобальном кэше преобразование файлов отложить до включения.
Переход выполнять последовательно и возобновляемо, с журналом и фиксацией новой
привязки только после успешной подготовки. Ошибка/отмена/завершение процесса не
должны стирать исходное дерево или сбрасывать сеанс. Не запускать полный пересчёт
всех аудиофайлов в главном потоке при первом открытии приложения.

Неизвестные каталоги, например от уже удалённого профиля или аккаунта без
сохранённого UID, не удалять и не назначать наугад: предложить отдельный импорт.
Прежний общий корень и журнал его удаления нельзя очищать целиком после
преобразования одного профиля — внутри ещё могут находиться остальные владельцы.

## Ручной выбор папки

1. Новый формат и тот же UID: подключить готовые файлы к текущему профилю.
   Новые локальные ID профиля не мешают. Неверный аккаунт — сообщить владельца
   кэша и предложить подходящий профиль/другую папку, не перепривязывать молча.
2. Прежний формат: распознать старый v1-корень/наборы JSON, аудио, обложек и
   контрольных сумм. Показать объяснение перед преобразованием: сохранённые
   исправные файлы будут использованы, обратная совместимость со старым
   приложением не обещается. Не выдавать преобразование за повторную загрузку.
3. Пустая папка или обычные пользовательские файлы: создать отдельную служебную
   подпапку. Соседние документы и музыка не становятся собственностью кэша.
   Неподдерживаемую более новую версию формата не преобразовывать в старую и не
   перезаписывать: сообщить о необходимости подходящей версии приложения.
4. Несколько старых владельцев: показать найденные наборы и сопоставить нужный
   текущему профилю; не объединять всё дерево как кэш одного пользователя.
5. Если оба расположения содержат кэш текущего аккаунта, предложить подключение
   с объединением по ID треков. Копировать только недостающее, исправный целевой
   файл не заменять без причины. При копировании проверять место/суммы и удалять
   исходный собственный каталог только после успешного подтверждённого переноса.

У старого формата на диске нет UID владельца: имя каталога — необратимый хэш
локального profileId и accountId. После потери данных приложения нельзя достоверно
вычислить прежнего владельца только по этому имени. Поэтому ручной legacy-импорт
должен сверять ID файлов со списком «Мне нравится» выбранного аккаунта.
Если подходящего подтверждённого списка нет и сеть недоступна, отложить эту
проверку и удаление, а не считать список пустым. Новый формат с UID устраняет
эту неопределённость для следующих переносов.

После подключения синхронизация сохраняет совпадающие исправные файлы,
докачивает недостающие и удаляет снятые лайки только внутри управляемого корня
этого профиля по подтверждённому списку. Неизвестные наборы старых владельцев и
посторонние файлы родительской папки не удаляются.

## Жизненный цикл и критерии проверки

- USB недоступен/доступ отозван: показать причину; не переключаться молча на
  другую папку с повторным скачиванием. При возвращении носителя использовать
  прежнюю привязку после проверки доступа.
- Удаление профиля: внутренний кэш очищать; пользовательский по умолчанию
  сохранять для повторного подключения, удаление его файлов — отдельный явный
  выбор. Так закрывается D-008 без потери переносимого пользовательского кэша.
- Старые приложения не обязаны читать новый формат. Не переиспользовать старую
  папку от имени нового профиля без проверки принадлежности и состава.
- Отдельный временный буфер волны, MP3-экспорт, авторизация и восстановление
  воспроизведения не меняются этой доработкой.

До выпуска проверить обновление с настоящего 144 (несколько профилей/оба вида
хранилища), чистую установку с legacy/new копиями и новыми UUID, разные UID,
потерю сети/USB, отмену и смерть процесса на стадиях преобразования/переноса,
недостаток места, посторонние файлы, два профиля с одним аккаунтом, удаление
профиля, глобальное отключение и повторное включение. Проверить Android 6+ и
современный SAF; после удаления приложения внешний кэш должен сохраниться и
подключиться на чистой установке. Все новые тексты — на восьми языках.

Исходная проверка кода и Android-документации:
[жизненный цикл 2.8.0](OFFLINE_CACHE_LIFECYCLE_2026_11_14.md).
Описанные миграция и формат пока не реализованы и не проверены тестами.
