# M12.7 — смена профиля при медленном чтении медиатеки

Дата: 2026-09-30. Подписанная beta 2.0.0beta-build56.
Актуальный остаток работ: [PROJECT_STATUS](PROJECT_STATUS.md).

Два новых инструментальных сценария воспроизвели ошибку AndroidPlayback:
при задержке `playbackWindow` на 1,2 секунды периодический `publish` показывал
трек outgoing-профиля уже под incoming-профилем. `detach` затем сохранял старый
трек и позицию в checkpoint нового профиля. Использованы настоящие SAF/WAV
файлы, Media3 и изолированные SharedPreferences; задержка явно удерживает
асинхронное чтение. До исправления оба сценария упали
([XML](qa/m12-7/baseline.xml)). Это доказанная ошибка, не предположение о USB.

Таймер и `detach` теперь публикуют/сохраняют данные движка только вне `restoring`.
Выбранный profile ID сохраняется отдельно при начале restore: остановка службы
не меняет сохранённый трек/позицию нового профиля, следующий запуск возвращается
к нему. Завершение чтения использует прежний путь установки/сохранения трека.
Новых очередей, индексов и модулей не добавлено.

После исправления оба сценария прошли
([XML](qa/m12-7/targeted-fixed.xml)): старый трек не появляется в новом профиле,
остановка службы во время чтения сохраняет его checkpoint, новый экземпляр
восстанавливает нужный трек на 0:12 и паузе. Обратный переход возвращает owner
на прежний трек и 0:03.

Первый общий прогон: 188 сценариев, четыре ошибки и шесть пропусков
([XML](qa/m12-7/full-before-final-fixes.xml)). Три ошибки относятся к подготовке
тестов: ClipHandoff оставлял вторую папку от предыдущего сценария;
CloudPlaylist задавал коллекцию до открытия общего каталога, который законно
запрашивает треки; LocalPlayback ожидал ещё не размещённую LazyColumn-строку
без прокрутки. Теперь сценарии готовят собственные папки, задают раздел после
перехода и прокручивают строку поиска.

Четвёртая ошибка выявила дополнительное последствие запрета checkpoint во время
IO: остановка сразу после изменения повтора теряла новый режим. Повтор/shuffle
теперь сохраняются сразу при изменении состояния, до обновления окна метаданных.
После всех исправлений прошли восемь сценариев без пропусков
([XML](qa/m12-7/final-targeted.xml)), включая две новые проверки HLS/DASH M9.6.

Окончательный общий прогон: **191 сценарий, 190 прошли, один пропущен,
без ошибок** ([XML](qa/m12-7/final-full-android15.xml)). Единственный пропуск —
двухфазный BootCheckpoint, которому нужен внешний reboot между фазами.
Публичные HTTPS-пробы Яндекса и overlay разрешены только на эмуляторе;
они прошли, не пропущены. `app:lintDebug` и `test` прошли;
[JVM](qa/m12-7/jvm-summary.txt) — 86 проверок без ошибок, неизменённые задачи
Gradle могут быть UP-TO-DATE.

На Android TV API 29 прошли пять новых сценариев (два профильных и три клипов)
без ошибок ([прогон](qa/m12-7/tv-profile-and-video.txt)).

## Отдельный reboot

Первый TV seed не дошёл до reboot: fixture получала SAF-grant перед удалением
старого корня, которое освобождало разрешение. Grant теперь выдаётся после
forget ([seed](qa/m12-7/tv-boot/seed.txt)). Phone seed/verify затем прошли.
Первый TV verify после этой правки всё ещё не восстановил current
([результат](qa/m12-7/tv-boot-final/verify.txt)); seed завершался до записи
окончательного checkpoint на диск. Диагностика указывает на незавершённые
асинхронные записи при завершении instrumentation. При дополнительном ожидании
полный TV reboot прошёл ([verify](qa/m12-7/tv-boot-traced/verify.txt)).
В окончательном тесте вместо ожидания seed проверяет position в prefs и
синхронно завершает уже подготовленную запись через пустой `edit().commit()`.
Это барьер только фикстуры; тест проверяет восстановление записанного состояния,
не устойчивость последних миллисекунд к аварийному отключению питания.
Диагностический listener удалён. Окончательные seed/verify прошли на обоих
эмуляторах: [телефон](qa/m12-7/phone-boot-accepted/verify.txt),
[TV](qa/m12-7/tv-boot-accepted/verify.txt). Трек, один ручной ID и 0:09
восстановились на паузе после полного Android reboot.
