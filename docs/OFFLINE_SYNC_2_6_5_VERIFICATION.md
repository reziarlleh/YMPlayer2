## Причины

1. PublicArtwork отправлял content:// в HTTPS-loader. Сохранённый PNG после
   переноса кэша читался через ContentResolver, но не отображался на экране.
2. Каждый обычный sync вызывал valid(reuseProof=false) для сохранённых аудио и
   обложек. При большой коллекции заново читались все тела файлов и обновлялись
   JSON. Быстрый catalog124 ускорял открытие списка, но не эту операцию.
3. Одного URI недостаточно для повторного чтения восстановленной картинки.
   Даже size/mtime/SHA могут остаться прежними после ремонта. Для каждой записи
   новой обложки сохраняется отдельная ревизия, которую учитывает UI-кэш.

## Реализация

- planSync использует свежий bulk inventory и индекс метаданных. Проверяет
  наличие, допустимый/ожидаемый размер, маркер завершения и известное повреждение.
  Готовые строки публикуются одним пакетом; JSON не переписываются для всего списка.
- syncIncremental сначала загружает отсутствующее аудио, затем обслуживает
  метаданные/обложки старых записей. Автоматическая загрузка нового лайка использует
  тот же путь. Старые store.sync/load остаются строгими.
- **Проверить и восстановить кэш** явно повторяет SHA всех сохранённых файлов.
  Работает через существующий OfflineSyncService с прогрессом/отменой. Нужны
  аккаунт и сеть по прежней политике Wi-Fi: проверка начинается со свежих лайков.
- Известное повреждение отмечается .invalid без удаления ожидаемой SHA.
  Даже после отмены следующий быстрый проход не принимает известный плохой файл
  за готовый. Успешное восстановление снимает маркер.
- PublicArtwork читает file/content/android.resource через ContentResolver,
  ограничивает объём входа и размер декодирования. Ключ UI включает ревизию.
  Отсутствующая исходная обложка остаётся настоящим состоянием «без картинки»;
  логотип не записывается вместо неё в кэш.
- Добавлены три сообщения во всех восьми языках и описание двух команд в RU/EN.
  Оба руководства явно отмечают, что новая команда ещё не входит в stable124.

## Текущая проверка реализации

Первая успешная сборка: JVM прошли, native API28 —4/5. Оба red-сценария стали
зелёными; ремонт SAF-картинки и отмена foreground full-check с последующим
восстановлением известного повреждения тоже прошли. Сценарий1000+2 не дошёл
до sync: seed был записан в родительскую папку store, а перенос создаёт
YMPlayer2-offline-UUID. Исправлена именно заготовка теста: передаётся фактический
documentId текущего кэша, с прежней проверкой разрешённой области провайдера.
Эта попытка не считается измерением скорости большой коллекции.

Дополнительно усилена ревизия картинки: UUID сохраняется при каждой успешной
записи, повторный ремонт проверяется при прежних URI, размере и грубом mtime.
Повторная сборка/native и release lint выполняются. Готовность пока не заявлена.

Следующая сборка/JVM/release lint прошла:0errors/82warnings. У Lint SARIF reporter

Первый regression API28:25/26. Исправленная WAV-заготовка metadata index прошла,
но старый gatedRead с4s deadline ошибочно назвал холодный legacy-проход блокировкой.

Это исправляет смешение скорости хоста с запрещённым IO; не выдаёт первый legacy

## Границы

Быстрая докачка не является новым криптографическим аудитом готовых файлов.
У legacy-записей без ожидаемого размера используются маркеры завершения;
скрытое изменение байтов того же размера выявляют полный audit и проверка
выбранного аудио, с прежним ограниченным повторным использованием playback proof.
Первое перечисление большого/медленного носителя остаётся O(N); время сервера
Яндекса и реальной USB-памяти не подменяется эмуляторным временем.
Физический часовой сценарий владельца и его личная приёмка не заявляются.
