# Версии и релизы YMPlayer2

Исходные формат, начальная версия и сквозной Build зафиксированы владельцем
2026-09-09. Действующее правило достижения целей версии уточнено 2026-10-28;
датированные решения ниже сохраняются как история, а не отменяют это уточнение.

## Действующее правило с 28 октября 2026

1. Перед началом цикла зафиксировать `baseVersion` (`MAJOR.MINOR.PATCH`),
   согласованные цели и критерии их завершения/проверки.
2. Пока эти цели не завершены, `MAJOR.MINOR.PATCH` не повышать ради промежуточных
   попыток, доработок и исправлений. Растёт только сквозной `Build`/`versionCode`:
   `X.Y.Z-buildN` → `X.Y.Z-buildN+1`. Не выдавать каждую попытку за новый patch.
3. Следующий номер версии выбирать для следующего согласованного набора целей
   после закрытия текущего. MAJOR/MINOR/PATCH описывают масштаб следующего цикла,
   а не число попыток довести текущий до результата.
4. Каждый новый APK продукта получает новый Build; ранее выделенный номер не
   переиспользуется, включая неудачные, непринятые и отозванные кандидаты.
   Копия того же APK сохраняет номер. Общий счётчик не сбрасывается при смене
   версии, канала или календарной даты.
5. Правила публикации, разрешённого канала, пакета, подписи и сохранения данных
   остаются прежними. Новое правило нумерации не разрешает автоматическую
   публикацию и не означает, что промежуточная сборка принята владельцем.

Первому этапу из [ROADMAP](ROADMAP.md) назначена **2.6.4**; все шесть целей
зафиксированы в [плане цикла](PLAN_2_6_4.md). `baseVersion=2.6.4`,
`releaseState=development`; новый Build выделяется только скриптом сборки.
Опубликованный стабильный выпуск **2.6.3-build119** и update feeds сохраняются
до завершения цикла и разрешения публикации. Пока цели не закрыты, номер2.6.4
не изменять ради промежуточных попыток.

## Самостоятельность продукта

- 2.x имеет отдельный репозиторий и цикл выпуска; поддержка 1.x продолжается отдельно.
- Android applicationId 2.x должен отличаться от 1.x. Обе версии должны
  устанавливаться рядом. Само число `2` в versionName этого не обеспечивает.
- Данные, настройки, кэш и авторизация изолированы. Импорт из 1.x, если понадобится,
  проектируется как отдельная пользовательская операция.
- Метаданные и артефакты обновлений 1.x и 2.x разделены. Каждый обновлятор принимает
  только свой продукт и разрешённый канал; числовое сравнение `2 > 1` недостаточно.
- Каркас использует отдельный `dev.petrov.ymplayer2`; provider authorities,
  app-specific actions и авторизация привязаны к продукту 2.x (M1/M4/M12).
- Beta и stable внутри 2.x используют одну идентичность устанавливаемого приложения:
  переход между ними — обновление 2.x с сохранением его данных.

Android определяет идентичность приложения через applicationId:
[Android Developers — Configure the app module](https://developer.android.com/build/configure-app-module).

## Формат

| Назначение | Формат | Пример |
| --- | --- | --- |
| Разработка и проверка | `MAJOR.MINOR.PATCHbeta-buildN` | `2.0.0beta-build1` |
| Стабильный релиз | `MAJOR.MINOR.PATCH-buildN` | `2.0.0-build18` |

`beta` и `build` пишутся строчными буквами, пробелы и ведущие нули отсутствуют.
`XXX` в обсуждении означает произвольное число, а не фиксированную ширину номера.
Первый beta — `2.0.0beta-build1`; доказательства конкретного артефакта находятся
в `releases/2.0.0beta-build1/` и [отчёте M1](M1_VERIFICATION.md).

## Сквозной Build

1. `N` — положительное целое, начиная с 1, общее для всех выпусков продукта 2.x.
2. Каждый новый APK, передаваемый для проверки или выпуска, получает новый номер,
   больший всех ранее выделенных. Beta, stable и параллельные ветки используют
   один счётчик; версия продукта и календарь его не сбрасывают.
3. Номер выделяется до сборки и не переиспользуется для другого артефакта.
   Пропуски после неудачных сборок допустимы. Копия того же APK сохраняет номер.
4. Снятие beta меняет versionName и требует новой сборки с очередным Build.
   Например: `2.0.0beta-build17` → `2.0.0-build18`.
5. Сборочный процесс должен хранить счётчик в одном источнике и исключать коллизии
   при параллельной работе. Не вычислять его по числу коммитов, дате или локальной
   ветке. В M1 используется [Build-Release.ps1](../tools/Build-Release.ps1):
   общий Git-каталог даёт lock/counter для связанных worktree. Сейчас издатель
   один; независимые клоны требуют общего реестра перед параллельным выпуском.
6. Запуск тестов, редактирование документов и компиляция без выпуска нового
   проверяемого APK сами по себе не расходуют номер.
7. Для Android принять `versionCode = N`, а versionName формировать по таблице выше.
   Начальный versionCode 2.x равен 1 и не зависит от versionCode приложения 1.x.

Внутренний debug для локальных автотестов использует отдельный applicationId
`dev.petrov.ymplayer2.dev` и ненумерованное имя `<baseVersion>-internal`. Он не распространяется
как beta. Каждый APK, выдаваемый владельцу для проверки, собирается release-скриптом
со сквозным номером. Beta и stable продукта используют `dev.petrov.ymplayer2`.

При публикации резервного APK файл в `releases/` добавляется в Git явно
(`git add -f releases/<version>/YMPlayer-<version>.apk`): общее правило
`.gitignore` скрывает случайные сборочные APK. До создания манифеста тег релиза
должен указывать на коммит, содержащий этот файл; скрипт
[Prepare-UpdateManifest.ps1](../tools/Prepare-UpdateManifest.ps1) проверяет
это условие. GitHub Release с APK публикуется до изменения манифеста `main`,
чтобы обновлятор не получил ссылку на ещё не опубликованный файл.

Android использует числовой versionCode для порядка версий, а versionName — для
отображения пользователю:
[Android Developers — Version your app](https://developer.android.com/studio/publish/versioning).

## Как выбирать PATCH, MINOR и MAJOR для следующего набора целей

Следующий набор целей планируется после закрытия текущего; его номер выбирается
до начала работ. Эти категории не требуют повышать версию при каждом исправлении
или новом кандидате внутри уже выбранного цикла.

| Часть версии | Масштаб следующего согласованного цикла | Пример масштаба |
| --- | --- | --- |
| `PATCH` | Законченный набор исправлений и небольших улучшений существующих сценариев | Исправление восстановления очереди, настройка уже существующего экрана |
| `MINOR` | Крупная новая возможность, законченный новый пользовательский сценарий или существенное развитие продукта | Полноценные загрузки и офлайн-библиотека, если их ещё не было |
| `MAJOR` | Новое поколение продукта либо намеренная несовместимость значимого внешнего контракта или данных | Переход, требующий отдельного плана совместимости и миграции |

Примеры определяют масштаб, а не обещают конкретные функции или сроки.
При повышении MINOR PATCH сбрасывается в 0; при повышении MAJOR — MINOR и PATCH.
Build при этом продолжает расти. Номер `2.0.10` допустим: после `2.0.9` нет
автоматического перехода на `2.1.0`. Количество коммитов и строк кода не является
критерием MINOR. Пока цели выбранного цикла не закрыты, сохранять его
`baseVersion` и увеличивать только Build.

Решение владельца от 2026-09-25: первый stable `2.0.0-buildN` включает весь
согласованный объём [дорожной карты](ROADMAP.md), кроме внешних скинов.
Пользовательские скины, готовые темы и руководство их авторов составляют
отдельный цикл `2.1.0beta-buildN+1` после 2.0.0; Build остаётся сквозным.

Проект использует собственную продуктовую схему, а не строгий SemVer:
`2.0.0beta-build1` не является SemVer, а `2.0.0-build18` трактовался бы SemVer
как предварительная версия. Поэтому общий SemVer-парсер не использовать для
определения стабильности или порядка наших обновлений. Канал хранить отдельным
полем (`beta`/`stable`), порядок совместимых обновлений определять по Build.
Сначала проверять идентичность продукта и разрешённый канал.
Основание различия: [Semantic Versioning 2.0.0](https://semver.org/).

## Когда снимать beta

Beta снимается, когда завершён и проверен весь заявленный объём конкретного
релиза. Одна готовая функция не делает стабильным приложение с незавершёнными
включёнными сценариями. При этом не требуется реализовать всю будущую дорожную
карту: готовые модули могут составить небольшой законченный первый релиз.

Для выпуска должны быть выполнены следующие условия:

- Объём и критерии приёмки заранее записаны; все включённые функции завершены.
- Релевантные тесты, проверки ошибок и регрессий проходят; нет известных
  блокирующих дефектов в заявленных сценариях.
- Новые модули проверены совместно с готовыми. Для UI проверены заявленные
  размеры, ориентации и масштаб текста.
- Проверен итоговый релизный APK после изменения versionName: идентичность,
  версия, подпись и основные сценарии запуска. При наличии обновлятора проверен
  путь beta → stable внутри 2.x.
- Сборочная проверка и проверка на целевом устройстве записаны отдельно.
  Необходимая приёмка воспроизведения и аппаратных интеграций не заменяется
  успешной компиляцией или индексом RepoWise.
- Документация, карта миграции и заметки о выпуске актуальны.
