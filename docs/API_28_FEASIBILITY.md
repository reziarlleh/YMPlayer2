# Возможность поддержки Android 9 / API 28

Дата: 2026-10-05. База анализа: stable **2.3.4-build79**, `main`,
commit `2f3917567b35ad203e022229096e6d102879d962`.
Это оценка возможности, а не реализованная совместимость и не новый выпуск.
Фактические Gradle-конфигурации и update feeds сохраняют минимум API 29.

## Вывод и границы

Снизить **minSdk с 29 до 28** технически возможно: переписывать аудиодвижок,
провайдер Яндекса или интерфейс по результатам анализа не требуется.
Одна замена номера недостаточна: обнаружены три места с обращениями к API 29.
`targetSdk = 36` и `compileSdk = 37` понижать для поддержки Android 9 не нужно.
Никакой отдельной ветки, beta или номера Build этим исследованием не создаётся.

## Подтверждённые изменения, необходимые перед выпуском

| Место | Текущее поведение и проблема на API 28 | Необходимое решение |
| --- | --- | --- |
| [OfflineSyncService](../app/src/main/kotlin/dev/petrov/ymplayer2/OfflineSyncService.kt), строка 26 | Безусловный `startForeground(id, notification, type)`; перегрузка введена в API 29, на 28 возможен `NoSuchMethodError` при запуске синхронизации | На 29+ сохранить тип службы; на 28 использовать двухаргументный вызов или совместимый helper |
| [DiagnosticsJournal](../app/src/main/kotlin/dev/petrov/ymplayer2/DiagnosticsJournal.kt), строки 74–88 | Экспорт через `MediaStore.Downloads`, `RELATIVE_PATH`, `IS_PENDING`; Downloads введён в API 29. `catch (Exception)` не защищает от ошибки связывания класса/метода | Добавить путь сохранения для 28 через SAF `ACTION_CREATE_DOCUMENT` либо приватный файл и безопасную передачу; не выдавать лишнее разрешение на весь накопитель только ради отчёта |
| [SafLibrary](../library/local/src/main/kotlin/dev/petrov/ymplayer2/library/SafLibrary.kt), строка 235 | `MediaMetadataRetriever().use` приводит объект к AutoCloseable, реализованному с API 29. Внешний `runCatching` может скрыть ошибку: теги/обложка/длительность не будут прочитаны, созданный retriever не освобождается этим путём | Явный `try/finally` и `release()` с сохранением обработки повреждённых тегов |
| 11 Android-модулей и канал обновлений | Во всех Android-модулях `minSdk = 29`; updater отклоняет manifest с минимумом выше устройства | При реализации согласованно изменить minimum в модулях; в манифестах нового выпуска указывать 28 только после проверки подписанного APK |

Официальные основания: [перегрузки Service.startForeground](https://developer.android.com/reference/android/app/Service#startForeground(int,%20android.app.Notification,%20int)),
[MediaStore.Downloads](https://developer.android.com/reference/android/provider/MediaStore.Downloads),
[сохранение через SAF](https://developer.android.com/training/data-storage/shared/documents-files#save),
[изменение MediaMetadataRetriever в API 29](https://developer.android.com/sdk/api_diff/29/changes/android.media.MediaMetadataRetriever).

## Что уже допускает API 28

- Манифесты проверенных закреплённых AAR Media3 ExoPlayer/Session 1.11.0,
  Activity 1.13.0, Core 1.19.0 и Compose UI 1.12.0 требуют минимум API 23.
  [Результат чтения AAR](qa/api28-feasibility/dependencies.json).
  Слияние debug-манифеста полного приложения с временным minSdk 28 прошло:
  конфликта минимального SDK с зависимостями в этом варианте нет.
- SAF для папок и USB, SQLite и приватный офлайн-кэш не требуют общей модели
  доступа Android 10. Для этих существующих путей понижение не требует
  автоматически добавлять READ/WRITE_EXTERNAL_STORAGE.
- У ClipActivity есть ветка старых fullscreen-флагов до API 30,
  у SideBarService — двухаргументный foreground-вызов до API 34,
  у StorageMonitor — прежняя регистрация receiver до API 33.
  Поддержка панели по-прежнему относится к K4811, а не ко всем магнитолам.
- В updater `SigningInfo` и `longVersionCode` доступны начиная с API 28;
  для старого archive parser уже запрашиваются оба signing-флага.
  [SigningInfo](https://developer.android.com/reference/android/content/pm/SigningInfo).
  Ослаблять проверку подписей или разрешать произвольный APK не требуется.
- Собственный файл перехвата Java-падений остаётся доступен. Системная история
  завершений процесса доступна только с API 30 и уже недоступна на нынешнем
  минимуме 29: это не новая потеря относительно Android 10.

## Выполненная проверка

RepoWise context использован для навигации, затем прочитаны реальные исходники
служб, экспорта, fullscreen, storage и updater. Проверены все объявления minSdk.
Gradle init-script изменял minimum только в диагностическом запуске, не в Git.
Второй проход включает `lint.checkDependencies = true`, чтобы учитывать
Android-модули проекта. Команды и итог находятся в
[сводке проверки](qa/api28-feasibility/lint-summary.json),
[init-script](qa/api28-feasibility/probe.init.gradle).

Первый проход `:app:processDebugMainManifest :app:lintDebug` завершил merge
и компиляцию debug-кода, затем остановился на двух `NewApi` error и 34 warnings.
Это ожидаемые ошибки исследуемого порога 28, а не доказательство неисправности
опубликованного APK с минимумом 29. Полный проход с зависимостями нашёл
**42 errors / 54 warnings**, включая третье `NewApi` в SafLibrary.
Контрольный проход с тем же расширенным анализом и minSdk 29 дал
**39 errors / 53 warnings**: набор всех ошибок кроме NewApi совпадает.
Следовательно, SDK-разница — три `NewApi` и связанное `InlinedApi` warning.
39 общих ошибок (37 UnstableApi opt-in, SuspiciousIndentation, WrongConstant)
зарегистрированы отдельно как [B-009](BUG_REPORT.md#b-009--расширенный-lint-модулей-не-проходит-p3).
Обычный прежний app lint не включал эту полную область проверки.
Предупреждение `InlinedApi` о DATA_SYNC относится к тому же foreground-вызову;
его исправление входит в первый пункт таблицы. Остальные lint-предупреждения
не следует объявлять новыми регрессиями API 28 без сравнительной проверки.
После контрольного прохода сгенерированный debug-манифест снова имеет minSdk 29.

Release APK для API 28 не собирался и не публиковался. Авторизация,
воспроизведение, клипы и установка обновления на Android 9 не проверялись.
Lint не устанавливает фактическую совместимость декодеров и прошивки.

## Риски и цена поддержки

1. **Старые прошивки и кодеки.** На конкретном Android 9 могут отличаться
   декодирование клипов, аппаратное ускорение, audio focus и работа в фоне.
   Доступность API не подтверждает исправность vendor-компонентов. Это риск
   дополнительной платформы, а не установленная поломка музыки или волны.
2. **Доступ к файлам и системные диалоги.** Новый экспорт нужно проверить
   при выборе места, отмене, ошибке записи; SAF/USB — после переподключения
   и перезапуска. Поведение прошивки не следует заменять предположением.
3. **Обновление и данные.** Нужна установка подписанного выпуска и следующего
   поверх него на API 28 с сохранением профилей, кэша и скинов. Уже работающая
   проверка сертификата должна сохраниться. Проверка манифеста не заменяет
   установку через системный installer.
4. **Постоянная матрица проверок.** Добавляется API 28: будущие зависимости
   и новые системные вызовы должны сохранять этот минимум. Ветки совместимости
   требуют проверки и на современных Android; без неё можно исправить Android 9
   и повредить актуальный путь службы/экспорта.

## Последовательность при отдельном решении о реализации

1. Исправить три места несовместимости с сохранением поведения на API 29+.
2. Согласованно изменить minimum 11 Android-модулей; повторить lint с зависимостями.
3. На API 28 проверить запуск, кодовую авторизацию, local/SAF, Яндекс/волну,
   фон/пульт/клипы, cache off и синхронизацию, новый экспорт и signed update.
   Проверить изменённые пути и на API 29/современном Android.
4. Публиковать в той же линии 2.3.x: новый signed Build, оба feeds, требования
   в README и обеих инструкциях, карта функций, статус и отчёт. Физическое
   устройство и AOSP-эмулятор различать в результатах.

Реализация не запущена. Текущий порядок утверждённых исправлений остаётся в
[ROADMAP](ROADMAP.md), следующий программный шаг — B-006.
