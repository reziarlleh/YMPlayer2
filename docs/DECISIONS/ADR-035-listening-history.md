# ADR-035 — история фактического прослушивания

Дата: 2026-10-02. Цикл: [2.3](../PLAN_2_3.md).

## Решение

Контракт `ListeningLog` находится в core; Android-адаптер `ListeningHistory`
в существующем library/local. Отдельная SQLite-база добавляется без изменений
каталога, очередей, профилей, аккаунтов и кэша. Транзакция обновляет запись
и оставляет последние 500 разных треков каждого профиля. Порядок — sequence,
не часы устройства; время сохраняется для подписи.

PlaybackState.playing выражает намерение playWhenReady и может быть true
во время загрузки. Поэтому запись вызывается AndroidPlayback по фактическому
Media3.isPlaying, только при совпадении ID текущего элемента и его метаданных.
Повторные события одного воспроизведения не пишут базу; пауза/повтор позволяют
новое прослушивание. Периодический уже существующий publish покрывает случай,
когда дисковые метаданные пришли после события Media3. Предзагрузка не пишет историю.

В базе только метаданные: нет URI аудио, разрешений SAF, токенов и подписанных
потоков. Локальная запись при показе разрешается через действующий индекс,
Яндекс — через текущий профиль/аккаунт/кэш. Восстановление метаданных в lookup
не предоставляет доступ: получение потока использует существующий API.

Запуск из истории создаёт обычный список из одного выбранного трека через
`playQueue`, как запуск списков каталога. Это не очередь всех 500 записей.
Первоначально использовался `select`; явный список выбрали для однозначного
поведения истории независимо от действующей очереди, как в других списках.
Сбой теста на телефоне оказался неверным нажатием: центр строки попадал на
кликабельное имя артиста и открывал карточку, а не вызывал playback.
Трассировка показала отсутствие команды запуска; тест нажимает справа на play.
Это не доказательство ошибки алгоритма `select`; очередь не исправлялась.

## Проверки

Нативная SQLite-проверка: лимит, повтор, страницы, USB, профили, новый экземпляр,
очистка одного профиля, отсутствие URI. Media3-сценарии: пауза до старта,
фактический старт, волна с предзагрузкой, восстановление на паузе, офлайн,
повторный запуск Яндекс-трека после потери lookup. Телефон/TV проверяются отдельно.

При проверке старого теста ручной очереди обнаружен ConcurrentModificationException
в тестовом ArrayList запросов: I/O дописывал журнал одновременно с assert.all.
Журнал теста заменён на CopyOnWriteArrayList; алгоритм очереди не менялся.
Другой шаг этого теста ждал окончания I/O перед проверкой восстановления,
но отпускал движок сразу после постановки shuffle в очередь команд.
Теперь ожидание подтверждённого shuffle/repeat стоит до detach.
