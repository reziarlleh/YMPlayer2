# ADR-001 — самостоятельный Android-продукт и модульная архитектура

Дата: 2026-09-09.
Статус: самостоятельность, нумерация и UI-композиция A приняты владельцем;
Kotlin/Compose и минимальные четыре модуля используются для M1.

## Контекст

1.x — работающий reference с Java Views, крупными Activity/repository/service,
одним TokenStore и тесным использованием Yandex DTO. 2.x требует профилей,
полной медиатеки и нового адаптивного UI при независимой установке и поддержке.

## Решение

1. Отдельные repository/applicationId/data/update feed; правила VERSIONING.md.
2. Предложить Kotlin/Compose shell, чистые domain contracts и provider/backend
   adapters. Конкретные зависимости выбрать совместимым стабильным набором при M1.
3. Playback имеет одного владельца; сеть/кэш/коллекция адресуются профилем/аккаунтом
   и поколением сессии. UI наблюдает state и отправляет команды.
4. Каталог метаданных отделён от файлов и политики скачивания. SAF и Яндекс
   реализуют свои capabilities; локальные треки не зависят от Yandex DTO.
5. Сначала обзор UI на mock data, затем вертикальные функциональные сценарии.
   Стабильность модуля подтверждать поведением, а не неизменностью его файлов.

## Альтернативы и последствия

Копирование 1.x ускорило бы первоначальный запуск, но сохранило бы связность и
однопрофильную модель. Полный набор пустых Gradle-модулей увеличил бы затраты
без проверки границ. Поэтому стартуем с минимального shell, добавляя модули
при появлении их проверяемой ответственности.

Media3 — предложенный единый backend, не автоматический перенос: аудио 1.x
использует MediaPlayer, видео — ExoPlayer. До приёмки нужны сравнительные сценарии
волны, foreground/media session, CWG и локальных ресурсов.

Android-прототип и сценарии тестов должны подтвердить выбранную композицию;
техническое предложение не считается уже реализованным или проверенным на K4811.
