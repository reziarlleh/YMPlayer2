# ADR-012: очередь волны и подготовка следующего аудио

Дата: 2026-09-13. Исправление неполного переноса M6 по сообщению владельца
об остановке после второго трека. Reference 1.x остаётся неизменным.

## Документация и рабочие методы 1.x

Reference: `reziarlleh/YMPlayer`, commit `7d118b4e3ec8`, локальная копия `D:/_codex/YaPlay`.

| Правило | Документ/метод reference | Место в 2.x |
| --- | --- | --- |

| Полный ответ rotor может содержать текущий/уже известный трек | Release 1.0.0-beta.8; `YandexMusicClient.getMoreMyWave`, `WaveQueue.append/currentCursorTrackId` | `YandexWaveApi` возвращает кандидатов; `WaveLoader` выбирает один новый и его cursor |

Это перенос поведения, с сохранением границ `core` / provider / playback.
Java-сервис 1.x и его постоянный кэш не копируются в архитектуру 2.x.

## Найденные расхождения build12

1. Ошибка фоновой дозагрузки заполняла `waveIssue`, после чего `maintainWave`
   запрещал автоматические запросы. Даже временный сбой третьей рекомендации
   мог закончить воспроизведение на второй.
2. Адаптер оставлял первый элемент ответа до фильтрации всей истории. Уже
   прослушанный трек в начале мог скрыть новую рекомендацию дальше в ответе.
3. В очередь Media3 попадала ссылка на будущий трек без отдельной полной
   подготовки аудио. Прежние тесты подтверждали очередь и переход, но не
   выполнение правила предварительной загрузки файла из 1.x.
4. `onPlayerError` переводил волну в остановленное состояние с ручным повтором.
   Обработка неисправного трека из 1.x была перенесена не полностью.

Остановка воспроизведена на изолированном источнике: три временных сетевых
сбоя при запросе третьей рекомендации, затем исправный источник. Старый код
не достигает третьего трека. Это доказательство клиентского дефекта, а не
запись конкретного сетевого ответа с телефона владельца.

## Правила новой реализации

- Первое аудио начинает потоковое воспроизведение сразу. Затем запрашивается
  один следующий допустимый трек; следующие порции не выкачиваются заранее.
- Следующее аудио загружается и проверяется в фоне. Текущий трек продолжает
  играть. В Media3 добавляется готовый файл, поэтому ошибка будущего источника
  не должна прерывать текущий исправный трек.
- Повтор чтения аудио использует уже полученного кандидата. Новый запрос rotor
  нужен после отказа от недоступного/повреждённого трека, а не каждого сетевого сбоя.
- На конце очереди ожидание использует ту же задачу, без второго параллельного
  запроса. Pause/Stop, смена профиля/источника и выход отменяют автоматический старт.
- После исчерпания фоновых попыток конец трека получает собственную попытку
  продолжения. Постоянная ошибка после ограниченных повторов остаётся видимой
  с ручным повтором; авторизация/доступ не повторяются автоматически.
- При восстановлении состояние остаётся на паузе. Следующий элемент сохранённой
  очереди заново проходит подготовку после Play, если временного файла уже нет.
  Явный выбор такого элемента использует настоящий индекс Media3 либо загружает
  его как текущий: логическая очередь может содержать ещё не подготовленный хвост.
- Внутренняя пауза при ожидании/ошибке не меняет намерение пользователя продолжать.
  Её отложенное событие Media3 учитывается отдельно; явная Pause сохраняет приоритет.
- Временные файлы принадлежат активному профилю и экземпляру буфера. Хранятся
  только текущий и следующий файлы, до 128 MiB каждый (256 MiB, как верхняя
  граница временного кэша 1.x). Отмена очищает готовые файлы; временный файл
  отменённой операции удаляет её worker. Остатки старого процесса очищаются.
- Имена файлов случайны. OAuth, подписанные URL и данные API в файлы буфера
  или checkpoint не записываются. Это не M7: синхронизация постоянного офлайн-
  избранного по-прежнему ограничена только треками «Мне нравится».
