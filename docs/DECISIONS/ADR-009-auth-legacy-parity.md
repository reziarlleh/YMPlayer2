# ADR-009 — исправление переноса входа из 1.x

2026-09-11. Уточняет ADR-008. Повод: после подтверждения кода у Яндекса владелец
увидел в build7 сетевую ошибку при возврате из браузера на Android 15 / HyperOS.
Момент возникновения и исходное сетевое исключение неизвестны. Приписывать сбой
ограничениям HyperOS без диагностики нельзя.

## Сверка с рабочим 1.x

RepoWise и актуальные исходники `D:/_codex/YaPlay` проверены повторно. Репозиторий
1.x и его пользовательские данные не изменялись. Источники поведения:

- `MainActivity.java`: `prepareDeviceLoginCode`, `startDeviceLogin`, `testAccount`.
- `ymusic/YandexMusicClient.java`: `requestDeviceCode`, `pollDeviceToken`, `open`.
- `ymusic/TokenStore.java`: `save`.

| Действие | Рабочий 1.x | Расхождение build7 | Исправление |
| --- | --- | --- | --- |
| Получен OAuth-токен | Сразу сохраняется; сведения Музыки запрашиваются отдельно | Не сохранялся до успешного account/status | Сначала атомарно сохранить OAuth, затем отдельно обновить сведения |
| Сбой при ожидании | Подготовленный код остаётся для повторной попытки | Первая сетевая ошибка удаляла код из состояния | Сохранять код, повторять ожидание до исходного срока истечения |
| HTTP | User-Agent `Yandex-Music-API`, X-Yandex-Music-Client `YandexMusicAndroid/24023621`, Accept-Language `ru` | Другой User-Agent, два заголовка отсутствовали | Вернуть заголовки 1.x |
| Тайм-ауты | Подключение 15 с, чтение 20 с | Чтение 15 с | Вернуть 15/20 с |

Исправляются подтверждённые различия реализации. Эта сверка сама по себе не
доказывает, какое из них вызвало ошибку на телефоне владельца.

## Состояние входа

Успешный OAuth завершается только после записи токена в собственное шифрованное
хранилище 2.x. Сведения Музыки необязательны: их отсутствие не отменяет вход,
не теряет токен и не требует повторного получения кода. Обновление доступно кнопкой
и при возвращении приложения на экран; после перезапуска незавершённое получение
сведений повторяется из сохранённого токена. Не подставлять фиктивные ID/имя.

Сохранённый OAuth не означает подтверждённого доступа ко всему музыкальному API.
Обработка отозванного/истёкшего токена при запросах каталога и refresh остаются M5.
Известный срок сохранённого токена уже проверяется перед восстановлением/повтором.

Схема содержимого шифрованного файла повышена до 2: пара ID/имя необязательна.
Чтение схемы 1 из build7 сохранено. AES-GCM, ключи профилей, AAD и исключение из
backup прежние. Архитектура открытых SharedPreferences из 1.x не переносится.
Выход удаляет сессию только выбранного профиля; поздняя запись не восстанавливает
её после выхода. При отмене до завершения записи токен откатывается.

## Ожидание и диагностика

В 1.x IOException останавливает текущий опрос, сохраняя подготовленный код.
В 2.x повтор автоматический, с увеличением задержки до 30 с, не чаще серверного
interval; числовой Retry-After учитывается. Всё ограничено исходным expires_in:
перезапуск сети не продлевает срок кода. HTTP 408/429/5xx распознаются до JSON,
поскольку ошибочный ответ сервера может содержать HTML.

Ожидание в 2.x по-прежнему начинается после выдачи кода, чтобы подтверждение с
другого устройства работало без открытия локального браузера. Это намеренное
отличие от 1.x. Код и предложение записать его остаются перед кнопкой браузера.

Пользователь видит безопасный код этапа/ошибки, например `TOKEN_TIMEOUT`,
`TOKEN_DNS`, `ACCOUNT_SERVICE` или `STORE_STORAGE`. Сырой ответ, исключение,
параметры клиента и токен в UI/журнал не выводятся. Проверки TLS не ослабляются.

Проверки и пределы приёмки: [M4.1](../M4_1_VERIFICATION.md).
