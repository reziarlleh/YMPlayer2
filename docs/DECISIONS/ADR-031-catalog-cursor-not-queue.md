# ADR-031 — каталог не является очередью воспроизведения

Дата: 2026-09-28; уточнено 2026-09-30. Область: M11/F04–F06/F16. Уточнение владельца после
[ADR-030](ADR-030-local-engine-window.md): для запуска музыки не нужен полный список
метаданных всех треков.

## Решение

- SQLite-индекс служит поиску, группам, фильтрам и выдаче видимых строк
  большой медиатеки. Экранная «страница» означает только порцию строк UI,
  а не страницу очереди воспроизведения.
- Сохранённый локальный плейлист — упорядоченный список ссылок на треки.
  Фактически это один JSON-файл с ID, порядком и короткими подписями для
  отключённого USB. Плеер читает текущую ссылку и следующую по этому порядку;
  SQLite-страницы для плейлиста не нужны. Оригиналы аудиофайлов не копируются.
- При запуске из всей локальной медиатеки, где пользовательского списка нет,
  достаточно текущего ID, фильтра источника и режима. Следующий/предыдущий
  доступный трек находится запросом к каталогу по ID. Shuffle выбирает
  доступный ID без загрузки всех метаданных в Media3; повтор при достижении
  конца возвращает первый доступный ID. Небольшая история нужна только если
  сохраняем действие «предыдущий» после shuffle.
- «Моя волна» остаётся отдельной сессией рекомендаций Яндекса. Следующий трек
  определяется ответом сервиса, а аудио для него готовится во время текущего.
  Для продолжения нужны текущий и один подготовленный следующий трек, сессия,
  cursor и минимальная история для обратного перехода/feedback. Её нельзя
  смешивать с локальным каталогом или заранее строить длинную очередь.
- Ручная очередь и пользовательский плейлист сохраняют явный порядок ID и
  операции редактирования. Это небольшой список ссылок, а не копия каталога.

## Состояние реализации

Экран автоматической локальной очереди получает страницу напрямую из SQLite
без промежуточной полной копии ID. `PlaybackState.queue` начиная с build49 показывает
только ближайшие метаданные (не более 29 треков) и абсолютную позицию, поэтому
UI не хранит вторую полную копию. Индекс умеет запросить соседний доступный
трек. После build49 обычный последовательный режим больше не удерживает вторую
полную копию в `AndroidPlayback.logicalQueue` ([M11.6](../M11_6_VERIFICATION.md)),
а [M11.10/build53](../M11_10_VERIFICATION.md) убирает постоянный полный снимок из `SafLibrary.state`. После [M11.7](../M11_7_VERIFICATION.md) естественный
локальный переход использует адресный запрос по ID. В build51
[M11.8](../M11_8_VERIFICATION.md) переносит на тот же контракт запуск,
дальний выбор, восстановление, обновление каталога и край подготовленного окна.
[M11.9](../M11_9_VERIFICATION.md) подключает shuffle/repeat ALL к тому же
адресному доступу: shuffle хранит только порядок ID и до трёх метаданных
в Media3, ALL возвращается к началу каталога, а не короткого окна.
Ручное редактирование и преобразование автоматического списка в ручной
читают ID и адресные метаданные. [M11.11/build54](../M11_11_VERIFICATION.md) оставляет ручной порядок ссылками,
а Media3 — максимум три соседних трека. Новый checkpoint и миграция проверены на Android 15;
объединение каталога с Яндексом остаётся открытым.
После [M6.5](../M6_5_VERIFICATION.md)
волна держит в активном списке максимум предыдущий/текущий/следующий трек;
до 4000 записей с метаданными для исключения повторов остаются отдельной
историей, не очередью Media3. ADR-030 описывает историческое поведение build47;
build50–54 заменили полные логические метаданные на описанный выше контракт.
M11 остаётся открытым из-за объединения каталога источников, а не этой прежней очереди.
