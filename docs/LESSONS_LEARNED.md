# Ошибочные решения и правила повторного использования

### 2026-10-09 — Bundle не заменяет настройки, SAF не универсален

rememberSaveable сохраняет состояние экрана, а не выбор пользователя после
любого завершения приложения. Режим оформления должен сохраняться сразу
при выборе независимо от жизненного цикла Activity. Наличие DocumentsUI
или доступа у другого приложения не доказывает доступ YMPlayer к USB.
Нужен доступ этого приложения; альтернативный обход должен проверяться
на публичной памяти с READ, а не только на приватной тестовой папке.
Попытка теста создать общий файл без WRITE закономерно отказала: исправлена
подготовка фикстуры, permission записи в продукт не добавлялся.
Дедупликация волны должна сохраняться отдельно от короткой очереди, а старый
курсор сам по себе не доказывает зацикливание сессии.
[Причины и свидетельства](PATCH_2_5_3_VERIFICATION.md).

### 2026-10-09 — диагностика удалённого пользователя должна быть выполнима

Предложенный ADB-скрипт оказался непригоден как обязательный шаг: пользователь
далеко и штатное ГУ может закрывать developer settings. Не требовать PC/root/ADB
для обычного багрепорта. Собственную сессию/уведомление собирать внутри YMPlayer
и экспортировать существующим способом; доступ к чужим плеерам не обещать
без отдельного права. [Коррекция плана](INSTRUMENT_CLUSTER_FOLLOWUP.md).

### 2026-10-09 — заполненные Android-поля не доказывают приёмку приборки

В beta99 положительные framework/CWG-проверки сосуществуют с отрицательным
пользовательским результатом на приборной панели. Гипотеза достаточности
DISPLAY_*/ART не подтвердилась. Следующая проверка — парные session/notification
снимки с проблемного ГУ; не закрывать D-003 и не объявлять очередное поле
причиной без нового доказательства. [Продолжение](INSTRUMENT_CLUSTER_FOLLOWUP.md).

### 2026-10-08 — ожидания теста сверять с базовым релизом

Первый связанный native-набор обнаружил старое ожидание current после пустого
офлайна. Исходник v2.5.1-build98 уже очищает очередь (B-019). Исправлено ожидание
теста, production не откатывался ради старого assert. Исходный отказ сохранён,
финальные API28/35 прошли по8/8.
[Доказательства](PATCH_2_5_2_BETA_VERIFICATION.md).

## ART нужно проверять на стороне framework-потребителя

8 октября: Media3 MediaMetadata.artworkUri не означает наличие bitmap ART.
LegacyConversions1.11.0 публикует ALBUM_ART/DISPLAY_ICON; extras Bitmap игнорируется.
Нельзя считать добавление URI исправлением bitmap-поля. Выбрано узкое build-time
дополнение той же сессии с явной защитой версии/сигнатуры. Runtime reflection
в приложение не добавляется. BuildSrc API подключается без транзитивного AGP
и Kotlin2.2.10, иначе возникают version/classpath-конфликты с текущим catalog.
[Решение](ADR_043_PLATFORM_METADATA_COMPATIBILITY.md), [проверки](PATCH_2_5_2_BETA_VERIFICATION.md).

## Архитектура APK и права исследовательского инструмента

8 октября FMPLAY ARM64 не установился в x86 AOSP. Полученный x86 имеет тот же
classes.dex и сертификат; ABI нельзя выдавать за различие MediaSession алгоритма.
Root-снимок API28 не доказывает разрешения обычного внешнего приложения: shell
там, в отличие от API35 стенда, не может читать все сессии. Проверять UID и
результат каждой команды. cmd media_session dispatch на API28 не реализован.
Не принимать stale UI XML после null root за текущий экран; использовать новый
путь снимка, проверять успешный dump. [Доказательства](FMPLAY_COMPARISON.md).

## Сначала проверять собственную стандартную публикацию

В D-003 первый план запросил оборудование и вынес Android Auto в кандидаты
до проверки реального release внешним Android-контроллером. Владелец отверг
это направление. Не выводить используемый способ запуска из отсутствия его
декларации в manifest. Не делать модель автомобиля/ГУ условием первичного
аудита metadata, состояний и permissions своего приложения.
Signed98/API35 показывает текст/bitmap даже при denied уведомлениях; ART пуст,
но framework getDescription работает. Ни общее «MediaSession есть», ни одно
различие поля не доказывают причину конечного симптома. Зафиксировать границы
и сравнить стандартные выходы приложений. [Доказательства](INSTRUMENT_CLUSTER_RESEARCH.md).

## MediaSession/CWG не доказывает передачу на автомобильную приборку

7 октября ответ в теме№17 объяснял работу сессии и лаунчера, тогда как
уточнение e.panchenko№18 описывает другой получатель: автомобильную приборку.
Не закрывать такой вопрос проверкой шторки, CWG или подрулевых кнопок.
Разделять публикацию Android, выбор/чтение OEM-получателем и конечный вывод.
Проверка общего MediaSession не закрывает конечный симптом. Начинать с
сравнения стандартных выходов приложений; различие ART/ALBUM_ART само по себе
ещё не причина. Следующий уточнённый порядок описан в отчёте.
[Сообщение, первичные источники и план проверки](INSTRUMENT_CLUSTER_RESEARCH.md).

## Первый запуск клипов и кэша: буферизация не пауза, каталог не аудит всех байтов

После stable97 владелец сообщил о двух Play и задержках Офлайна/волны.
Контроллер toggled playWhenReady, а кнопка показывала isPlaying: до готовности
декодера первый Play фактически отменял ожидающий запуск. Разделять запрос
и фактический звук; MEDIA_PLAY проверять по самому плееру, а не старому кадру UI.
Явное открытие Клипов отличается от автоматического восстановления Pause.

LikedFileStore.load хешировал всю коллекцию под общим Mutex; первый сетевой
трек ждал того же Mutex, хотя его не было в кэше. Быстрый локальный список
не требует SHA всех файлов. Полностью проверять выбранный аудиофайл, сохраняя
границы профиля/аккаунта и запрет сетевой подмены явного Офлайна.

Аудит97 проверял восстановление контроллера, но не отображение pending Play
и первый/повторно присоединённый реальный Surface. Дополнены native-сценарии
ClipActivity/MP4, сравнение со старым кодом и API35. Растяжение с фотографии
не воспроизвелось на baseline-эмуляторе; удачный тест геометрии нельзя выдавать
за физическую приёмку HyperOS. [Причины, проверки и границы](PATCH_2_5_1_VERIFICATION.md).

## Восстановление сеанса: intent, источник и профиль должны согласовываться

6 октября прежняя политика паузы после старта была заменена требованием
продолжать последний активный источник. Нельзя сохранять только isPlaying:
буферизация и автоматическая пауза видео в фоне не равны пользовательской Pause.
Нельзя автоматически проигрывать Music при создании AudioService: сервис может
быть создан для метаданных, а последним выходом могло быть Radio/Clip.
При смене профиля записывать MUSIC/paused для входящего профиля до restore;
иначе его старый RADIO/play может включиться при следующем cold start, хотя
фактически после переключения показывался остановленный музыкальный плеер.
Клип должен ставить музыку на паузу через gate даже если она ещё восстанавливается.
[Проверки и свидетельства](SESSION_RECOVERY_2_5_VERIFICATION.md).

Кандидаты88–91 резервировались до окончания всех lifecycle-проверок и не
публиковались. Выпускной номер резервировать после финализации кода; старые
локальные APK не переименовывать/переиспользовать. Последний опубликованный
до задачи build87 сохранялся до финального92.

Постоянная навигация меняет подготовку старых тестов: Local/Radio должны явно
выбирать начальный экран. Remote-событие разрешено посылать только после
получения фокуса своим окном. Эти ошибки фикстур сначала воспроизведены,
потом адресно исправлены/проверены; не подгонять продукт под прежний default.

RepoWise: после большого изменения обычный cascade50 оставил часть страниц
stale, doctor исправил рассинхронизацию SQL/FTS/vector. Повтор с --since базы
задачи и cascade500 перестроил311 страниц без модельной генерации. `--full`
в этой версии требует provider даже с --index-only; не запускать LLM ради
структурного индекса. Symbol search всё ещё может не вернуть новый класс,
который присутствует в SQL: отсутствие выдачи не доказывает неиспользование.
[Свидетельство и ограничения индекса](qa/session-recovery-2026-10-07/repowise.json).

## FM OAuth prototype, кандидат85 →86

В первой beta85 отчёт правильно различал отсутствие FM UID и несовпадение UID,
но UI сводил оба случая к тексту «Радио не вернуло UID». Проверка только boolean

кандидат85 не опубликован, новый APK получает86. [Доказательство и прогоны](YANDEX_RADIO_AUTH_PROBE.md).

- TV requestFocus нельзя автоматически переносить на телефон в touch mode.
  TV-сценарий scoped по устройству, остальные радио-проверки проходят на API28.

## Каталоги Радио / beta93

- Не помещать suspend-ответ прямо в `state.value.copy(...)`: Kotlin сначала
  вычисляет receiver; параллельный ответ возвращает устаревшую копию. Сначала
  await, затем copy текущего state. Проверять обе очередности реальных задержек.
- Guard повторного cursor относится к продолжению списка. Первая страница
  после смены вкладки/refresh не должна сравниваться с cursor прежнего списка.
  Happy-path следующей страницы недостаточно: нужен Collection→All и refresh.
- При вложенных horizontal/vertical scroll `performScrollTo` дочерней кнопки
  может прокручивать только ближайший LazyRow. Проверять видимость и прокрутить
  внешний список перед касанием. Сбой автоматизации нельзя исправлять в аудио.
- Возврат из Dialog асинхронен. Для аппаратного фокуса использовать реальный
  DPAD, а не ожидать keyboard focus в touch mode телефона.

Падение прежнего порядка await, повторяемый cursor и исправленные прогоны:
[отчёт](RADIO_CATALOG_2_5_VERIFICATION.md).

## Выход из внешней Activity / beta94

Shell не должен переключать свою route на экран-заглушку перед запуском внешнего
видеоплеера. Сохранение активного output/позиции не доказывает правильный экран
после Back: проверять выбранный реальный раздел, системную и экранную кнопки,
восстановленную Activity и отсутствие повторного открытия после явного Close.
Persisted active route и underlying return route — разные значения.

После автоматической догрузки удалять дублирующую ручную команду, сохраняя явный
Retry после ошибки. Проверять догрузку всех страниц без нажатия More.
В TV-тесте входить в non-touch mode реальным DPAD: ранний прогон после touch
оставил RequestFocus без фокуса. Исправлена подготовка стенда, не продуктовый плеер.
[Причина, исходный отказ и проверки](CLIP_BACK_2_5_VERIFICATION.md).

## Сетевые экраны / beta95

Ошибка API/HTTP500 не доказывает отсутствие интернета. Системная VALIDATED может
не подтверждаться при доступном сервисе; fallback не должен требовать HTTP200
или токен. Любой достоверный TLS/HTTP ответ показывает связь, а не исправность API.
Новый вход/Retry начинает полный grace, смена экрана/профиля отменяет прежний check.
Reconnect отменяет pending запрос старой сети; late reply не заменяет новый ответ.
Callbacks фонового shell не должны запускать музыку за видео. Ожидание первого
подключения клипа привязано к STARTED, а recovery использует checkpoint.

Thread.sleep не продвигает Compose test clock. У первого UI-теста timeout4 сек
не наступал ожидаемый grace: исправлены virtual clock и подготовка профиля,
продуктовый интервал5 сек не уменьшен. Реальная потеря сети/клипы прошли уже
в исходном прогоне; исходные логи сохранены. [Проверки](INTERNET_2_5_VERIFICATION.md).

## Выпускной аудит2.5 / stable97

- Обычный computed val route захватывает прежнее значение в callback до следующей
  композиции. Delegated derivedStateOf читает state при событии. Проверять nav+Back
  в одном UI-кадре: отдельный native-тест сначала доказал B-017.
- Пагинация требует не только нового cursor, но прироста уникальных объектов при
  append. Повторяющаяся страница иначе бесконечно запрашивается (B-015).
- Отмена родителя ради карточки требует восстановления незагруженного запроса,
  а не пустой копии loading=false. Загруженные страницы не сбрасывать (B-016).
- Нельзя переводить любую строку «Неизвестный исполнитель»: это может быть настоящее
  имя. Пустой тег отделять при чтении, старый metadata-cache инвалидировать и читать
  оригинал; ID/first-seen сохранять, недоступные неоднозначные строки не угадывать.
- prefs.clear не сбрасывает живой контроллер между instrumentation-тестами.
  RadioLive должен явно очистить query/filter/tab, UI-тест — выбрать экран/прокрутить
  строку. Изолированное прохождение на старом APK отличает setup от нового бага.

Исходные отказы, исправления и повторные проверки: [аудит](AUDIT_2_5_RELEASE.md).
